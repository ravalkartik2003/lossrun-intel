## Key Question 1 — Visualization layer options for embedding in a React app (custom charts vs Power BI Embedded vs Azure Managed Grafana vs Fabric)

### Takeaway
For sub-second slider/drill-down interactions over 1,000–5,000 claims inside the insurer's own React app, custom charts (ECharts or Recharts) plus TanStack Table over an in-memory per-account dataset is the lowest-latency, cheapest and most WCAG-controllable option; Power BI Embedded (app-owns-data on an F SKU, from US$0.36/hr for F2) is the most "credible to insurer evaluators" option for the static report/pricing-memo views, but every slicer/what-if move is a server round-trip that bypasses the render cache, and the docs give no way to set what-if parameters from the host app. Azure Managed Grafana and Fabric Embed are not fits (Entra-only auth with no documented app-owns-data embedding; Fabric Embed is preview and Real-Time-Dashboards-only).

### Inferences
- Cost floor for a credible Power BI path: an F2 (~$0.36/hr ≈ $263/mo PAYG, pausable) supports app-owns-data embedding with no per-viewer licensing, which is far cheaper than the A1 (~$1.01/hr) that older guidance implied; A SKUs remain purchasable but the F line is where Microsoft is investing. (The per-model memory limit on F2 was not fetched; see Gaps.)
- For the sub-second what-if/drill-down requirement, Power BI's own documents work against it: every slicer/filter change bypasses the render cache and re-queries the capacity, the smallest SKUs throttle interactive requests under sustained overload, and nothing documents a host-app API for what-if parameters (the parameter is a measure over a GENERATESERIES slicer; setting it via `setSlicerState` with an `IAdvancedFilter` on the parameter column is plausible but unverified). A POC that must prove p95 ≤ ~1 s with 25 concurrent underwriters is safer on custom charts over client-held data.
- A hybrid is the most credible to evaluators: custom React analytics (ECharts canvas for dense scatter/large-loss plots, Recharts/SVG for small accessible charts, TanStack Table for claim drill-down) for interactive work, plus one Power BI report embedded (F2, service-principal, RLS by account) for the "official" UW report package and export. This reuses the client's existing Power BI skills and gives a governed semantic model for the analytics catalog.
- WCAG AA is a differentiator for the custom path: Recharts 3's accessibility layer and ECharts' aria/decal options are documented, whereas Microsoft does not state that embedded Power BI reports inherit its consumer accessibility features; the "Show visuals as tables" option is still preview.
- Azure Managed Grafana (observability-oriented, Entra-only, no documented embed) and Fabric Embed (preview, Real-Time Dashboards only, delegated auth only) should be excluded with a one-line rationale in the brief.

### Gaps
- Max semantic-model memory for F2/F4 (below A1) was not retrieved; the SKU limits table is linked from the capacity page but not fetched.
- No documentation or working sample was found for driving a what-if parameter from the embedding host; the only community thread has no solution.
- No published benchmark of Power BI Embedded slicer-interaction latency on small SKUs; Microsoft explicitly declines to give a users-per-SKU table.
- Azure Managed Grafana and Fabric pricing pages rendered "$-" placeholders; only Fabric's blog/third-party hourly figures were obtained (US West 2).
- Plotly.js WebGL (scattergl) performance and bundle sizes for ECharts/Plotly/Nivo were not obtained from primary sources.

## Key Question 2 — What-if recalculation: client-side vs server-side, consistency with "official" numbers, showing delta vs baseline

### Takeaway
At 1,000–5,000 claims per account the whole dataset fits comfortably in browser memory (TanStack Table is documented to handle tens of thousands of rows client-side), so sliders should recompute in the browser (plain JS in a web worker, or DuckDB-Wasm if SQL expressiveness is wanted) against a server-computed, cached "as-reported" baseline; consistency is proven by running the same metric definitions server-side (persisted snapshot) and client-side (golden tests), and the UI shows scenario minus baseline per metric.

### Cited Findings
- DuckDB-Wasm runs SQL asynchronously in web workers, uses Apache Arrow as the data protocol, reads local/remote files and in-memory buffers, caps memory at 4 GB (WebAssembly), is single-threaded by default (multithreading experimental) — [DuckDB docs: Wasm overview](https://duckdb.org/docs/2.0/clients/wasm/overview.html); bundles `mvp`, `eh` (needs Wasm exception handling) and `coi` (threads; requires COOP/COEP cross-origin isolation and a pthread worker); jsDelivr, webpack, Vite and self-hosted loading documented — [DuckDB docs: Instantiation](https://duckdb.org/docs/2.0/clients/wasm/instantiation.html); ingestion via `registerFileBuffer/registerFileURL/registerFileText`, `insertArrowTable`, `insertCSVFromPath`, `insertJSONFromPath`, Parquet by name; Arrow major version must match (`^17`) — [DuckDB docs: Data ingestion](https://duckdb.org/docs/2.0/clients/wasm/data_ingestion.html); npm `@duckdb/duckdb-wasm` latest tag 1.33.1-dev57.0, MIT — [npm registry](https://registry.npmjs.org/@duckdb/duckdb-wasm/latest)
- The DuckDB-Wasm VLDB paper reports TPC-H geometric-mean query times of 0.003 s (SF 0.01), 0.013 s (SF 0.1) and 0.073 s (SF 0.5) versus SQL.js 0.012/0.142/0.809 s and Arquero 0.023/0.268/2.822 s, measured in Node.js v17 on a Ryzen 5800X (not in a browser); the engine is in-memory and positioned as complementing servers for "browser-sized data subsets" — [Kohn et al., VLDB 2022](https://www.vldb.org/pvldb/vol15/p3574-kohn.pdf)
- TanStack Table: client-side row models are "a good fit" for a few thousand rows and designed for "10s of thousands of rows"; watch total fetch size and browser memory; server-side (`manualPagination`) only when data can't be held in the browser — [TanStack Table: Pagination guide](https://tanstack.com/table/latest/docs/guide/pagination)
- CQRS: separate read models/materialized views optimized for queries; combine with event sourcing where the event store is the write model and read models are projections; accept eventual consistency; use the transactional outbox when the read store is separate — [Azure Architecture Center: CQRS pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)
- `HybridCache` (`Microsoft.Extensions.Caching.Hybrid`, .NET 9+, also targets .NET Standard 2.0/.NET Framework 4.7.2): L1 in-process + optional L2 `IDistributedCache` (Redis/SQL), `GetOrCreateAsync`, stampede protection per key, tag-based invalidation via `RemoveByTagAsync`, System.Text.Json by default — [Microsoft Learn: HybridCache](https://learn.microsoft.com/en-us/aspnet/core/performance/caching/hybrid)
- Azure SQL read scale-out (Premium/Business Critical/Hyperscale): route analytics with `ApplicationIntent=ReadOnly`; replica lag "tens of milliseconds to single-digit seconds" with no fixed upper bound; not available on General Purpose — [Microsoft Learn: Read scale-out](https://learn.microsoft.com/en-us/azure/azure-sql/database/read-scale-out)
- SQL Server temporal tables give `FOR SYSTEM_TIME AS OF` point-in-time queries with system-managed history — [Microsoft Learn: Temporal tables](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables); EF Core maps them with `.ToTable("Claims", b => b.IsTemporal())` and exposes `TemporalAsOf/TemporalAll/TemporalBetween/TemporalFromTo/TemporalContainedIn` — [Microsoft Learn: EF Core temporal tables](https://learn.microsoft.com/en-us/ef/core/providers/sql-server/temporal-tables)
- Browser responsiveness target: Interaction to Next Paint "good" is ≤ 200 ms at the 75th percentile, "poor" above 500 ms — [web.dev: INP](https://web.dev/articles/inp)

### Inferences
- Recommended pattern: on account open, the API returns one normalized claims payload (≤5k rows, likely < 2 MB JSON/Arrow) cached per account/version with HybridCache (tag = accountId, invalidated on new upload or override). The React app holds it in Zustand; every slider (reserve ±10 %, exclude catastrophes, trend factor) recomputes all catalog metrics in a web worker in a few milliseconds—well under the 200 ms INP "good" bar—so chart updates are sub-second with zero server round-trips. DuckDB-Wasm is optional; it costs a multi-megabyte Wasm download and adds Arrow version coupling, so plain TypeScript metric functions (shared with unit tests) are the pragmatic POC choice, with DuckDB-Wasm reserved for ad-hoc SQL exploration.
- "Official" numbers: the server computes the as-reported baseline from the same metric library (a C# port or a shared JSON-defined metric spec executed by both sides), persists it as a versioned feature snapshot (CQRS read model) and stamps it with the catalog version; the client never persists what-if results, only labelled scenarios (inputs) if the user saves one. Golden-file tests assert client and server produce identical values for the reference set, which doubles as evidence for the "insight accuracy vs reference set" acceptance criterion.
- Delta display: each KPI tile shows baseline, scenario and signed delta (absolute and %), with the scenario parameters printed in the pricing memo so an actuary can reproduce them; temporal tables let the server answer "as of" questions (what the baseline was at quote time) without a separate snapshot store.
- Scale note: 25 concurrent underwriters × one account payload each is trivial for an API behind HybridCache; the server-side path is only needed for cross-account (portfolio) analytics, where Azure SQL read scale-out or a Fabric/Power BI semantic model fits.

### Gaps
- No primary-source browser benchmark for DuckDB-Wasm on 1–5k-row aggregations (paper numbers are Node.js TPC-H); bundle sizes are not stated in the docs.
- No vendor or Microsoft reference implementation found that documents client-side what-if recomputation for underwriting specifically.

## Key Question 3 — Lineage model: source cell → normalized field → feature, with OCR polygons, spreadsheet cells, mapping/model versions and per-field confidence; standards; click-to-highlight UIs

### Takeaway
Both Azure extraction services emit exactly what a lineage record needs — page number, 4-point polygon (inches for PDF, pixels for images, clockwise from top-left), confidence 0–1 and character spans — but only for rendered files (PDF/images); XLSX inputs get spans and sheet-as-page numbering with no coordinates, so spreadsheet lineage must record the cell address from the workbook itself. Model the chain as PROV-style entities (source region → extracted field → normalized field → feature) with OpenLineage-style column-level transformation types, and render "click value → highlight in PDF" with react-pdf-highlighter's viewport-independent `ScaledPosition`.

### Cited Findings
- Document Intelligence (v4.0 GA 2024-11-30) Layout output: `pages` (unit, width, height, angle), `words` with `polygon` + `confidence` + `span`, `lines`, `paragraphs` with `boundingRegions`, `tables` with `cells` (rowIndex, columnIndex, spans, kind, `boundingRegions`), `figures`, `sections`; `boundingRegions` = `pageNumber` + `polygon`; `spans` = offset/length into the top-level `content` string; Office files: DOCX/HTML count 3,000 chars as a page, each XLSX worksheet is one page, each PPTX slide one page; "Table analysis is not supported for XLSX input" — [Document Intelligence Layout model (Azure China mirror of Learn)](https://docs.azure.cn/ai-services/document-intelligence/prebuilt/layout)
- Coordinates: images in pixels, PDFs in inches; polygon points clockwise from top-left relative to the element's orientation (top-left, top-right, bottom-right, bottom-left); currently only 4-vertex quadrilaterals; multi-region elements (e.g., tables across pages) get an array of regions; "DOCX, XLSX, PPTX, and HTML files aren't rendered, so no bounding regions are returned"; spans default to grapheme clusters, switchable via `stringIndexType` to UTF-16 for .NET — [Microsoft Learn: Analyze document response](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response)

## Key Question 4 — Audit/override model: event-sourced change log, immutable storage, proving "100 % of edits tracked", as-reported vs as-adjusted

### Takeaway
Use Azure SQL append-only ledger tables (GA since 2022; UPDATE/DELETE blocked at the engine, SHA-256 Merkle-tree digests uploaded every 30 s to immutable Blob or Azure Confidential Ledger) as the audit log, temporal tables for the mutable claim-field state, and an explicit override command that writes the override row and audit event in one transaction; prove completeness in the demo with a reconciliation query (history versions = audit events), a failed UPDATE on the ledger table, and `sp_verify_database_ledger`.

### Cited Findings
- Ledger (SQL Server 2022+, Azure SQL Database, SQL MI): updatable ledger tables (system-versioned with history table + ledger view) and append-only ledger tables ("updates and deletes are blocked at the API level"); rows are SHA-256 hashed into Merkle trees per transaction and per block, blocks chain to the previous block hash; the latest block hash is the database digest, stored externally in Azure Blob immutable storage, Azure Confidential Ledger or on-prem WORM; verification recomputes hashes and reports inconsistencies; a *ledger database* can contain only ledger tables and cannot be converted back — [Microsoft Learn: Ledger overview](https://learn.microsoft.com/en-us/sql/relational-databases/security/ledger/ledger-overview)
- Azure SQL Database ledger moved from preview (2021) to GA (2022) — [Microsoft Learn: Azure SQL Database what's new archive](https://learn.microsoft.com/en-us/azure/azure-sql/database/doc-changes-updates-release-notes-whats-new-archive)
- Append-only table DDL: `CREATE TABLE [AccessControl].[KeyCardEvents] (...) WITH (LEDGER = ON (APPEND_ONLY = ON));` — an UPDATE then errors; who/when query: `SELECT t.commit_time, t.principal_name, l.*, l.ledger_operation_type_desc FROM [AccessControl].[KeyCardEvents_Ledger] l JOIN sys.database_ledger_transactions t ON t.transaction_id = l.ledger_transaction_id`; only `ENABLE LEDGER` permission is listed as a prerequisite — [Microsoft Learn: Create append-only ledger tables](https://learn.microsoft.com/en-us/sql/relational-databases/security/ledger/ledger-how-to-append-only-ledger-tables); updatable form `WITH (SYSTEM_VERSIONING = ON (HISTORY_TABLE = …), LEDGER = ON)`, `LEDGER = ON` optional only in a ledger database — [Microsoft Learn: Create updatable ledger tables](https://learn.microsoft.com/en-us/sql/relational-databases/security/ledger/ledger-how-to-updatable-ledger-tables)
- Ledger view columns: `ledger_transaction_id`, `ledger_sequence_number`, `ledger_operation_type` (1 INSERT / 2 DELETE), `ledger_operation_type_desc`; an UPDATE on an updatable table shows as DELETE + INSERT; append-only tables add 2 GENERATED ALWAYS columns, updatable add 4 — [Microsoft Learn: Updatable ledger tables](https://learn.microsoft.com/en-us/sql/relational-databases/security/ledger/ledger-updatable-ledger-tables), [Append-only ledger tables](https://learn.microsoft.com/sql/relational-databases/security/ledger/ledger-append-only-ledger-tables)
- Digests: with automatic storage configured, digests are generated every 30 seconds (none if no transactions) and uploaded to Azure Storage or Azure Confidential Ledger; manual `EXECUTE sp_generate_database_ledger_digest` returns JSON `{database_name, block_id, hash, last_transaction_commit_time, digest_time}` — [Microsoft Learn: Digest management](https://learn.microsoft.com/en-us/sql/relational-databases/security/ledger/ledger-digest-management); enable in portal under Security → Ledger → "Enable automatic digest storage" — [Microsoft Learn: Enable automatic digest storage](https://learn.microsoft.com/sql/relational-databases/security/ledger/ledger-how-to-enable-automatic-digest-storage)
- Ledger limitations: no TRUNCATE, no deleting older data from append-only or history tables, no converting an existing table to ledger (migrate data instead), no XML/sql_variant/UDT/FILESTREAM/VECTOR columns, drop-column data retained hidden, dropped tables renamed `MSSQL_DroppedLedgerTable_*` and recorded in `sys.ledger_table_history`; up to 200 ledger tables per transaction — [Microsoft Learn: Ledger limitations](https://learn.microsoft.com/en-us/sql/relational-databases/security/ledger/ledger-limits)
- Azure Confidential Ledger: customer-managed append-only ledger on Intel SGX enclaves with CCF consensus, verifiable receipts, "no one — not even Microsoft — is 'above' the ledger"; use cases include SQL ledger digest storage and audit trails; private vs public ledger types; deletion is hard delete — [Microsoft Learn: Confidential ledger overview](https://learn.microsoft.com/en-us/azure/confidential-ledger/overview); limits: 2 ledgers per subscription, 8 KiB per entry, "hundreds of writes per second" — [Microsoft Learn: Confidential ledger limits](https://learn.microsoft.com/en-us/azure/confidential-ledger/limits)
- Immutable Blob storage: WORM via time-based retention (1–146,000 days) or legal hold; container-level or version-level (requires versioning); locked policies are required for SEC 17a-4(f) and only extendable; Cohasset validated SEC 17a-4(f), FINRA 4511, CFTC 1.31(c)-(d); "Allow protected append blob writes" for append workloads like SQL backup/audit; incompatible with point-in-time restore and last-access tracking — [Microsoft Learn: Immutable storage overview](https://learn.microsoft.com/en-us/azure/storage/blobs/immutable-storage-overview)
- Azure SQL auditing writes `.xel` logs to append blobs, Log Analytics or Event Hubs; immutable storage needs "Allow protected append writes"; captures only the first 4,000 chars of statements; may drop events under very high load; server auditing changes GA July 2025 — [Microsoft Learn: Auditing overview](https://learn.microsoft.com/en-us/azure/azure-sql/database/auditing-overview)
- Cosmos DB change feed: "latest version" mode omits intermediate changes and deletes; "all versions and deletes" mode records every create/update/delete in order (NoSQL API only), requires continuous backup and is readable only within the backup window — [Microsoft Learn: Change feed](https://learn.microsoft.com/en-us/azure/cosmos-db/change-feed), [Change feed modes](https://learn.microsoft.com/en-us/azure/cosmos-db/change-feed-modes); "All versions and deletes mode is in preview and is supported for the change feed processor starting with version 3.60.0" with `ChangeFeedItem<T>.Metadata.OperationType` — [Microsoft Learn: Change feed processor](https://learn.microsoft.com/en-us/azure/cosmos-db/nosql/change-feed-processor); continuous backup tiers: 7-day (no backup storage charge), 30-day and 35-day ($0.20/GB × regions per month); restore $0.15/GB — [Microsoft Learn: Continuous backup](https://learn.microsoft.com/en-us/azure/cosmos-db/continuous-backup-restore-introduction)
- Event Sourcing pattern: append-only event store as system of record, materialized views for queries, immutable events give "a complete audit trail", snapshots for long streams, compensating events instead of edits, at-least-once consumers must be idempotent, GDPR handled by crypto-shredding or external PII; "poor fit" for prototypes/MVPs; apply selectively — [Azure Architecture Center: Event Sourcing](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)
- EF Core `ISaveChangesInterceptor` sample audits SavingChanges/SavedChanges/SaveChangesFailed but writes to a separate audit DB (not atomic) and records `CurrentValue` only; Microsoft calls it "not intended to be a robust auditing solution" — [Microsoft Learn: EF Core interceptors](https://learn.microsoft.com/en-us/ef/core/logging-events-diagnostics/interceptors)
- Entra audit log entries are "system generated and can't be changed or deleted" and include old and new values for changed properties, actor, target and correlation ID — [Microsoft Learn: Entra audit logs](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/concept-audit-logs)

### Inferences
- Data model: (1) `ExtractedValue` — immutable, one row per field per document version with lineage columns (Q3); (2) `ClaimField` — temporal table holding the *resolved* value with `OverrideId` nullable; (3) `Override` — append-only ledger table: {overrideId, claimId, field, oldValue, newValue, rationale (required), userId/UPN, role, utc timestamp, documentId+version, catalogVersion, scenarioId?, supersededBy?}; (4) `AuditEvent` — append-only ledger table for every mutation incl. uploads, re-extractions, permission changes, exports and quote pushes (event-sourcing vocabulary: `ClaimFieldOverridden`, `OverrideRevoked`, `FeatureSnapshotPublished`…). Overrides are never updated; a reversal is a new override row that supersedes the prior one.
- "100 % of edits tracked" demo script: (a) a single `OverrideClaimFieldCommand` handler is the only code path that writes `ClaimField`, and it writes `Override` + `AuditEvent` in the same SQL transaction; (b) reconciliation query — count of `ClaimField` history versions (`FOR SYSTEM_TIME ALL`) minus 1 per field equals count of `Override` rows; (c) live attempt to `UPDATE`/`DELETE` an `AuditEvent` row fails with the ledger error; (d) `sp_verify_database_ledger` against the latest digest in immutable Blob proves no tampering; (e) Azure SQL auditing to immutable append blobs shows every statement incl. DBA access. Together these cover user/time/old→new/rationale with tamper evidence.
- As-reported vs as-adjusted: compute feature snapshots twice — from `ExtractedValue` (as-reported) and from `ClaimField` resolved values (as-adjusted) — and store both with the catalog version; the UI toggle and the pricing memo show both plus the list of overrides that explain the difference. Temporal `AS OF` gives "as-adjusted at the time the quote was issued".
- Cosmos DB is a weaker fit for the audit store here: the only mode that captures every intermediate change is still preview and bounded by the continuous-backup window, whereas SQL ledger is GA, queryable with ordinary T-SQL and ships with external digest verification. Keep Cosmos (if used) for the document/lineage JSON, and use its change feed only as an outbox relay (Q6).
- Production path: lock the Blob immutability policy (SEC 17a-4-grade) only for the audit/digest containers; keep the POC on an unlocked policy to allow teardown.

### POC implementation note (ADR 0010)
- **Guarantee statement for the audit & governance model:** tamper protection is **preventive** on `ExtractedValue`, `Override` and `AuditEvent` (append-only ledger tables: the engine rejects UPDATE/DELETE, and digests in immutable Blob make history verifiable) and **detective** on `Claim` (a temporal table: every change is versioned, and `lossrun-db audit-proof` flags any version without an audited decision). Production option: make `Claim` an updatable ledger table so claim rows are tamper-evident in the engine too.

### Gaps
- Microsoft's pages do not state explicitly that ledger tables can coexist with regular tables in a non-ledger database (the how-to examples imply it by creating tables with `LEDGER = ON` without a ledger database); verify in the POC.
- GA/preview status of Cosmos "all versions and deletes" is stated only on the change-feed-processor page ("in preview"); the modes page itself is silent.
- No source found quantifying ledger write overhead on Azure SQL.

## Key Question 5 — Role-based permissions (Entra ID groups + app roles, ASP.NET Core policies, applicant vs underwriter vs admin, auditing permission changes)

## Key Question 6 — Workflow integration with the quote management system (REST/webhooks/Service Bus), pricing memo generation, pushing annotations/flags, assigning follow-ups

### Takeaway
Use the Architecture Center's split — Service Bus (sessions, duplicate detection, dead-letter) for commands into the quote system and Event Grid/webhooks (CloudEvents, retries up to 24 h, dead-letter to Blob) for notifications — behind a transactional outbox so every pushed annotation/flag/follow-up is both audited and delivered at-least-once with idempotency keys; generate the pricing memo as DOCX with the MIT Open XML SDK (QuestPDF is excluded from its free Community licence for public-sector bodies, so PDF needs a paid licence or a DOCX→PDF step).

### Cited Findings
- Messaging choice: Service Bus for commands/business transactions (peek-lock, duplicate detection, sessions for FIFO, session state checkpoints, dead-letter queue, topics/subscriptions); Event Grid for discrete event notification (push to webhooks, at-least-once, no ordering, configurable retries/TTL/dead-lettering, CloudEvents preferred, HTTP pull option); Event Hubs for streams; consumers must be idempotent; claim-check for large payloads — [Azure Architecture Center: Asynchronous messaging options](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/messaging)

## Key Question 7 — Performance proof: load testing 25+ concurrent users with Azure Load Testing, measuring p95 of interactive actions, front-end budgets, caching, and what "sub-second chart interactions" implies

### Takeaway
Prove the API side with Azure Load Testing (JMeter/Locust; pass/fail on `response_time_ms` p95 and error %; 250 JMeter threads per engine so 25–100 users is a single engine) and the browser side with Application Insights JS custom events (`startTrackEvent/stopTrackEvent` around slider → chart-render) aggregated to p95, plus Playwright-driven synthetic sessions; architecturally, "sub-second chart interactions" means the per-account dataset is loaded once, cached (HybridCache) and recomputed client-side, so the API only needs to return a 1–5k-claim payload quickly and the browser must keep interactions within the ≤200 ms INP band.

### Cited Findings
- Azure Load Testing supports URL-based tests, Apache JMeter (all JMeter protocols/plugins) and Locust; fail criteria; auto-stop on error conditions; Azure Pipelines/GitHub Actions/CLI integration; server-side metrics via Azure Monitor (App Insights, Container insights); VNet-injected testing for private endpoints — [Microsoft Learn: What is Azure Load Testing](https://learn.microsoft.com/en-us/azure/load-testing/overview-what-is-azure-load-testing)
- Fail criteria: `response_time_ms` with avg/min/max/p50/p75/p90/p95/p96/p97/p98/p99/p999/p9999, `latency` (p50/p90/p95/p99), `error` percentage, `requests_per_sec`, `requests` count; test-level or per-request (`Request: p95(response_time_ms) > 1000`); up to 50 criteria; server-side criteria on Azure resources (Monitoring Reader role; not from pipelines); auto-stop default 90 % errors in a 60 s window — [Microsoft Learn: Define test fail criteria](https://learn.microsoft.com/en-us/azure/load-testing/how-to-define-test-criteria)
- Scale guidance: ≤ 250 threads (virtual users) per engine for JMeter, up to 500 users per engine for Locust; total VUs = threads × engines; engine is healthy if average CPU/memory stays below 75 % — [Microsoft Learn: Configure for high scale](https://learn.microsoft.com/en-us/azure/load-testing/how-to-high-scale-load); engines are Standard_D4d_v4 (4 vCPU/16 GB), JMeter 5.6.3 on JDK 21, Locust 2.33.2 on Python 3.9 — [Microsoft Learn: Key concepts](https://learn.microsoft.com/en-us/azure/load-testing/concept-load-testing-concepts)
- Limits: up to 400 engines per run, 24 h max duration, 50 criteria per test, client-side metrics retained 365 days, server-side 90 days, results/logs 6 months — [Microsoft Learn: Service limits](https://learn.microsoft.com/en-us/azure/load-testing/resource-limits-quotas-capacity)
- Secured endpoints: pass Entra/OAuth tokens or secrets from Key Vault (`GetSecret` in JMeter, env var in Locust), PKCS12 client certificates, or the load-testing resource's managed identity (which disables multi-region distribution); examples are API-level HTTP only — [Microsoft Learn: Test secured endpoints](https://learn.microsoft.com/en-us/azure/load-testing/how-to-test-secured-endpoints)
- Pricing: the official page lists two tiers (0–10,000 VUH and 10,000+ VUH) but rendered no dollar values — [Azure pricing: Load Testing](https://azure.microsoft.com/en-us/pricing/details/load-testing/); a Microsoft Tech Community thread quotes $0.15/VUH (0–10k) and $0.06/VUH (10k+) with VUH = users × hours (community answers, not official) — [Tech Community discussion](https://techcommunity.microsoft.com/discussions/azure/azure-load-test-pricing/4449198)
- Well-Architected PE:06 performance testing: define targets/thresholds/acceptance criteria (example: "If your SLO requires 95% of requests to complete within 200 ms, set the API response time threshold to 200 ms at the 95th percentile"), budgets per layer (e.g., API 400 ms, DB 150 ms, 1 % failures), load → stress → spike → soak, production-like environment, baselines and regression comparison, Azure Load Testing + App Insights — [Microsoft Learn: WAF performance testing](https://learn.microsoft.com/en-us/azure/well-architected/performance-efficiency/performance-test)
- Application Insights JavaScript SDK auto-collects page views and uncaught exceptions and exposes `trackEvent`, `trackMetric`, `trackPageViewPerformance`, `startTrackEvent/stopTrackEvent`, `trackDependencyData`, telemetry initializers; server-side should use OpenTelemetry — [Microsoft Learn: App Insights JavaScript SDK](https://learn.microsoft.com/en-us/azure/azure-monitor/app/javascript-sdk)
- Browser responsiveness: INP good ≤ 200 ms, poor > 500 ms, measured at p75 — [web.dev: INP](https://web.dev/articles/inp); performance budgets combine quantity metrics (bundle KB, requests), milestone timings (FCP, TTI) and rule-based scores, enforced with Lighthouse CI, bundlesize or webpack performance hints — [web.dev: Performance budgets 101](https://web.dev/articles/performance-budgets-101)
- Power BI embedded: measure from the `rendered` event; filters/slicers applied at embed time bypass cache; capacity load should be tested with a few dozen simulated users and extrapolated; autoscale on CPU/Overload metrics — [Embedded performance best practices](https://learn.microsoft.com/en-us/Power-Bi/developer/embedded/embedded-performance-best-practices), [Capacity planning](https://learn.microsoft.com/en-us/power-bi/developer/embedded/embedded-capacity-planning)
- Playwright Workspaces (Azure App Testing) provides cloud-hosted browsers for large-scale parallel Playwright runs with traces/recordings; the overview does not describe performance measurement — [Microsoft Learn: Playwright Workspaces](https://learn.microsoft.com/en-us/azure/app-testing/playwright-workspaces/overview-what-is-microsoft-playwright-workspaces)

### Inferences
- Test plan that maps 1:1 to the acceptance criteria: (1) JMeter plan with 30–50 threads on one engine replaying the real API sequence (auth → account open → claims payload → feature snapshot → override POST → memo export), 15–30 min soak, criteria `p95(response_time_ms) < X.X s` per request and `error > 1 %` fail, with App Service/SQL server-side metrics attached; (2) browser interaction p95 from App Insights `customEvents` (`slider.reserve.recalc`, `drilldown.open`, `chart.render`) collected during a scripted Playwright session with 25 parallel browsers; (3) Lighthouse CI budget on the analytics route (JS ≤ ~500 KB gz is reasonable with ECharts tree-shaken; INP ≤ 200 ms). ## Key Question 9 — The "analytics catalog" deliverable: documenting each metric so actuaries sign off; templates from dbt metrics / Power BI semantic models; CA-specific notes

### Takeaway
Model the catalog on dbt MetricFlow's governed YAML (name, label, description, type simple/ratio/derived/cumulative, expr/agg, numerator/denominator, filter, config.meta owner) extended with insurance-specific fields (valuation date, development caveats, CA cumulative-trauma treatment, reference-set tolerance), version it in git, and have the same spec drive both the server snapshot and client what-if code; WCIRB data (CT = 26 % of 2024 indemnity claims; 99 % of post-termination CT claims litigated; 127 % projected AY2025 combined ratio) justifies CT and litigation metrics as first-class catalog entries.

### Cited Findings
- dbt MetricFlow: semantic models declare entities (join keys), dimensions (time/categorical) and simple metrics; metric types simple, ratio, cumulative, derived, conversion; YAML is version-controlled so "data and business teams review and approve definitions"; MetricFlow generates SQL and chooses join paths — [dbt docs: About MetricFlow](https://docs.getdbt.com/docs/build/about-metricflow)
