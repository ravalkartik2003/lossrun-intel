## Key Question 1: Azure AI Document Intelligence (DI) — current state, limits, pricing, what changed 2025–2026

### Takeaway
DI v4.0 (API `2024-11-30`) is the current and only GA line; 2025–2026 brought only containers, tax-form refreshes, and retirement notices (v2.0 cloud API retired 31 Aug 2026; v2.1 end-of-support 15 Sep 2027; v3.0 end-of-support 30 Mar 2029). Microsoft's own October 2026 guidance now steers "custom extraction with no labels" and "high-variation documents" to Content Understanding, not DI custom models, while keeping DI for stable, bounded layouts and on-prem containers. Retail pricing: Read $1.50/1K pages, Layout/prebuilt $10/1K, custom extraction & custom generative $30/1K, classifier $3/1K, query fields $200/1K (!), add-ons $6/1K.

**Layout model (v4.0) capabilities**
- Tables: `rowSpan`/`columnSpan`, cell `kind` (e.g., `columnHeader`), bounding regions; "rotated tables are supported"; tables may have merged cells and odd angles; **table analysis is not supported for XLSX input**. Figures: `boundingRegions`, `caption`, cropped images with `output=figures`. Sections/paragraph roles: `title`, `sectionHeading`, `footnote`, `pageHeader`, `pageFooter`, `pageNumber`. Markdown: `outputContentFormat=markdown`; tables rendered as HTML so merged cells/multirow headers survive; selection marks as ☒/☐. Handwriting: per-line `styles.isHandwritten` + confidence (Latin only). Each page returns an `angle` field "indicating whether the page is rotated"; the page does **not** say the service auto-deskews. Async: poll every 3–5 s. — [Layout model, ms.date 2026-05-01](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0)
- Input limits (S0): PDF/TIFF up to **2,000 pages**, **500 MB** (F0: 4 MB, first 2 pages only); images 50×50 to 10,000×10,000 px; min text height 12 px at 1024×768 (~8-pt at 150 DPI); **"Password-locked PDFs: you must remove the lock before submission"**; Office (DOCX/XLSX/PPTX/HTML) max 8M characters; page units: XLSX = 1 page per worksheet, PPTX = 1 per slide, DOCX/HTML = 1 per 3,000 characters. Studio does not accept Office files (REST/SDK only). — [Read model input requirements, ms.date 2026-08-15](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/read?view=doc-intel-4.0.0)
- Office input support by model: Read, Layout and Custom classification accept DOCX/XLSX/PPTX/HTML; prebuilt and custom extraction models list only PDF/images. — [DI model overview, ms.date 2026-06-05](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/model-overview?view=doc-intel-4.0.0)
- Layout markdown is described as "LLM friendly"; no latency figures are published for Layout anywhere on Learn (checked RAG, Layout, FAQ pages). — [DI RAG concept, ms.date 2026-08-15](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/retrieval-augmented-generation?view=doc-intel-4.0.0)
- Response geometry: PDFs in inches, images in pixels; polygons are 4-vertex quadrilaterals clockwise from top-left; bounding regions only for rendered files (DOCX/XLSX/PPTX/HTML get none); figures/tables exclude captions. Field values normalized (`date` → ISO 8601, `currency` → `valueCurrency{currencySymbol,amount}`) with per-field `confidence`, `boundingRegions`, `spans`. — [Analyze document response, ms.date 2026-04-30](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)

**Add-ons and query fields**
- v4.0 add-ons: `ocrHighResolution`, `formulas`, `styleFont` are paid add-ons; `barcodes`, `languages`, `keyValuePairs` are free; searchable PDF is free with `prebuilt-read` 2024-11-30; `queryFields` is an add-on "priced differently", **max 20 query fields per request**, works with Layout and prebuilt models except W-2/1098/1099; add-ons do not support Office files. — [Add-on capabilities, ms.date 2026-08-15](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept-add-on-capabilities?view=doc-intel-4.0.0)

**Custom models (training, labels)**
- "You need only five examples of the same form or document type to get started"; template training 1–5 min; neural 30 min–12 h (default 30 min, paid training beyond); neural handles structured/semi/unstructured with one model for all variations; template needs one model per variation; both support signatures; v4.0 neural adds table/row/cell confidence. Limits: template 500 pages/50 MB; neural 50,000 pages/1 GB. — [Custom model, v4.0](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/train/custom-model?view=doc-intel-4.0.0)
- Quotas (S0): Analyze **15 TPS default (adjustable via support, not guaranteed)**, Get 50 TPS, max 2,000 pages/analysis, 500 MB; custom neural training: 10 free hours/month, requests over 20 in a calendar month billed at the training tier; max classifier doc types 1,000; min 5 samples per class. — [DI service limits, v4.0](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/service-limits?view=doc-intel-4.0.0)
- Custom classifier (v4.0): min **2 classes × 5 samples each**, max 1,000 classes, 100 samples/class, 25,000 pages/2 GB; `splitMode` = `none` (default in 2024-11-30!), `perPage`, or `auto` (identifies documents and page ranges); incremental training via `baseClassifierId`; output `documents[]` with `docType`, `boundingRegions[pageNumber]`, `confidence`. — [Custom classifier, ms.date 2026-08-15](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/train/custom-classifier?view=doc-intel-4.0.0)
- Confidence/accuracy: custom neural and generative models "don't provide accuracy scores during training"; word-level and table/row/cell confidence available for custom models from 2024-11-30; guidance to target ≥80% accuracy and add human review for financial/medical. — [Accuracy & confidence, ms.date 2026-04-08](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/accuracy-confidence?view=doc-intel-4.0.0)
- Batch analysis (v4.0): blob container input (managed identity recommended; SAS needs read/write/list/delete), **max 10,000 files per batch**, results written as `<file>.ocr.json` to a result container, batch status retained 24 h. — [Batch analysis, ms.date 2026-05-18](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/batch-analysis?view=doc-intel-4.0.0)

### Inferences
- For this POC, DI's role should be limited to (a) a fallback/second-opinion OCR+Layout engine and (b) the on-prem container story if an evaluator asks; its custom neural model is a poor fit because it needs ≥5 labelled samples **per carrier template** and offers no zero-shot path, and Microsoft itself now routes "no labels, high variation" to Content Understanding.
- The $200/1K "Query Pages" meter is a trap: if a developer tries `queryFields` as a cheap zero-shot extractor, cost could be 20× the layout call; confirm via metrics which meter is hit before using it.
- The DI .NET SDK (1.0.0, Dec 2024) is stable but stagnant; expect no new features surfaced through it.

### Gaps
- No official DI latency numbers exist on Learn (per page or per 30-page scan); only the "poll every 3–5 s" guidance. Must be measured in the POC.
- Whether DI auto-corrects skew (vs only reporting `angle`) is not stated in current docs.
- The custom generative model's status (preview/retired) could not be confirmed; its meter still exists but no doc page describes it in v4.0.
- Exact SOC/ISO/HIPAA in-scope listing for DI: the "cloud services in audit scope" page defers to appendices of a PDF that could not be fetched (see Q6).

## Key Question 2: Azure AI Content Understanding (CU) — what it is, GA status, fit for no-label extraction, pricing

### Takeaway
CU is GA (API `2025-11-01`, Nov 2025; .NET SDK `Azure.AI.ContentUnderstanding` 1.1.0 stable, Apr 2026) and is Microsoft's designated path for schema-described, zero-label field extraction with per-field confidence and `D(page,x1,y1,…)` source grounding; a `2026-06-01-preview` (Jul 2026) adds agentic mode, sync Read/Layout, in-page segmentation, signatures, and "advanced contextualization" training. Documents are billed at $1/1K pages (Read/"Basic") or $5/1K (Layout/"Standard") plus $1/1K pages contextualization ($3/1K for advanced/agentic) plus your own GPT token spend — no CU meter for field extraction itself. There is no insurance/loss-run prebuilt; you build a custom analyzer on `prebuilt-document`.

### Cited Findings

**What it is, status, versions**
- Timeline: `2024-12-01-preview` (Nov 2024) → `2025-05-01-preview` (May 2025: standard/pro modes, classification API, Office formats) → **`2025-11-01` GA (Nov 2025)** → Dec 2025 Read/Layout need no model → Mar 2026 SDKs GA (Python, .NET, Java, JS) → Jul 2026 **`2026-06-01-preview`** (agentic mode, synchronous Read/Layout, labeled-sample training improvements, signatures, metadata) → Aug 2026 preview SDKs → Sep 2026 CU CLI (preview). Previews `2024-12-01` and `2025-05-01` retire by 15 Jul 2026. — [CU What's new, ms.date 2026-09-08](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/whats-new); [Standard/pro modes, ms.date 2026-01-29](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/concepts/standard-pro-modes)
- Nov 2025 GA notes: "Content Understanding only charges for content extraction (per page/minute) and contextualization. Generative features directly use your Foundry model deployment incurring standard token-based charges." "Managed capacity for the preview generative models is retired. To use Content Understanding, you always bring your own Foundry large language model and embedding deployments." Dedicated classifier APIs deprecated in favor of `contentCategories` (200 categories, up from 50). Field count raised to 1,000. — [CU What's new](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/whats-new)
- .NET SDK: `Azure.AI.ContentUnderstanding` stable **1.1.0** (22 Apr 2026), prerelease **1.2.0-beta.3** (11 Aug 2026, carries `2026-06-01-preview` and `ToLlmInput()`); targets .NET 8.0 / .NET Standard 2.0, compatible with net10.0; main class `ContentUnderstandingClient`, analysis returns `Operation<AnalysisResult>`. — [NuGet Azure.AI.ContentUnderstanding](https://www.nuget.org/packages/Azure.AI.ContentUnderstanding)
- Microsoft's own .NET sample repo (`azure-ai-content-understanding-dotnet`) targets .NET 8, API `2025-11-01`, and covers ContentExtraction, FieldExtraction, Classifier (split + route), AnalyzerTraining (documents only), Management, ModelDeploymentSetup; it wraps REST rather than the SDK. — [GitHub Azure-Samples/azure-ai-content-understanding-dotnet](https://github.com/Azure-Samples/azure-ai-content-understanding-dotnet)

**How field extraction works without labels**
- Field methods: `extract` (literal text, documents only), `generate` (inferred/summarized), `classify` (enum). Field `description` "acts as a mini-prompt"; `method` optional in GA (service picks extract vs generate). Analyzer JSON: `baseAnalyzerId: "prebuilt-document"`, `models: {completion:"gpt-5.2", embedding:"text-embedding-3-large"}`, `config.estimateFieldSourceAndConfidence: true`, `fieldSchema.fields` with arrays of objects for line items. — [Create custom analyzer tutorial](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/tutorial/create-custom-analyzer); [Analyzer reference, ms.date 2026-09-15](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/concepts/analyzer-reference)
- Learn's "choose the right tool" page (ms.date 2026-06-02): "No labels, any document type: Use a CU custom analyzer (zero-shot). Describe fields in plain language. No labeling or training is required." DI custom model is for "custom extraction with labels for highly structured documents (claims, standard applications) — neural model training with as few as 5 labeled samples." Build-your-own on Azure OpenAI: "No confidence scores… you must either accept all results or review all of them… or build your own confidence model." — [Choosing the right AI tool](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/choosing-right-ai-tool)
- Best practices: define repeated data (line items) as arrays of objects, not JSON-in-string; write descriptions with location hints, format expectations and alias lists ("Equal to the 'Distributions' column. Also disclosed as 'Realizations' or 'Realized Proceeds'"); "Refine descriptions before adding labeled examples." Suggested confidence thresholds: critical ≥0.90, important ≥0.80, non-critical ≥0.70 (illustrative; "determine thresholds experimentally"). "Only document analyzers support confidence scores." — [CU best practices](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/concepts/best-practices)
- Utility analyzers: `prebuilt-documentFieldSchema` proposes a schema from a sample; `prebuilt-documentFields` extracts generic key-value pairs. Studio has an "AI suggestion" feature to propose a schema from uploaded samples. — [Prebuilt analyzers, ms.date 2026-01-29](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/concepts/prebuilt-analyzers); [Studio custom analyzer how-to](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/how-to/customize-analyzer-content-understanding-studio)

**Confidence and grounding (cell-level lineage)**
- Output per field: `valueString` (typed), `spans[{offset,length}]` into the top-level `markdown`, `confidence` (0–1), and `source` = `D({pageNumber},{x1},{y1},…,{x4},{y4})` (inches for PDF, pixels for images; pages 1-indexed; 4-point polygon clockwise from top-left). Table cells also carry `source`, `span`, `rowIndex/columnIndex/rowSpan/columnSpan/kind`. Pages carry `angle` (degrees). `source` is only returned for rendered inputs (PDF/image), **not** for DOCX/XLSX. — [Document elements](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/document/elements)
- Enable with `estimateFieldSourceAndConfidence: true` (analyzer) or `estimateSourceAndConfidence: true` (field); Jul 2026: "Confidence scores and source grounding are now available for all document field types, including fields that use the `generate` and `classify` methods" (preview and GA). Not available in pro mode. — [CU What's new](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/whats-new); [Standard/pro modes](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/concepts/standard-pro-modes)
- Pricing explainer: confidence/grounding "add token consumption, so they raise LLM costs" — no separate meter. — [Pricing explainer](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/pricing-explainer)

**Labeled samples (cheap bootstrapping)**
- "For datasets with minimal template variations, add a single labeled sample. For more complex variations, add a representative sample for each template or format." "Start by following the best practices for schema definitions. If you still see incorrect field values or confidence scores below your straight-through processing threshold, use labeled samples." In `2026-06-01-preview`, training "distills the relevant patterns and domain context from the labeled samples into the built analyzer," "reduces token consumption when the analyzer runs," and the built analyzer "neither retains nor requires access to the labeled documents." Training supports documents only, not `generate` fields; "Labeled samples don't correct text recognition problems." Studio workflow: upload sample → **Auto label** (runs the analyzer to prepopulate) → correct → rebuild. — [Analyzer improvement](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/document/analyzer-improvement)
- Training data limits: 1 GB, 50,000 pages/images; labeled samples specified as `knowledgeSources` (GA) and live in a customer-owned storage account tied to the Studio project. — [CU service limits](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/service-limits); [Migration preview→GA](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/how-to/migration-preview-to-ga)
- Advanced contextualization (2.0 preview) applies to `advanced.*` and `agentic.*` workflows "and to custom analyzers trained with labeled data" at the advanced rate. — [Pricing explainer](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/pricing-explainer)
- Microsoft's Oct 13 2026 benchmark (19 US tax-form categories, equal-weight mean F1): **DI 96.71% F1, $10/1K pages modeled cost, latency index 4.4; CU 1.0 GA 97.41%, $16.23/1K, index 10; CU 2.0 Preview (advanced contextualization) 99.32%, $8/1K, index 4.9** — i.e., 2.0 preview is +1.91 pts F1, −51% cost, −51% latency vs 1.0 GA, and +2.61 pts F1, −20% cost, +10% latency vs DI. Costs are "modeled benchmark estimates." — [Foundry blog, 13 Oct 2026](https://devblogs.microsoft.com/foundry/more-than-a-schema-content-understanding-prebuilt-analyzers/)

**Classification / splitting multi-carrier bundles**
- `contentCategories` (up to **200** categories per document analyzer, each with `description` and optional `analyzerId` to route the segment to a sub-analyzer; include an `other` category); `enableSegment: true` splits a multi-document file at page boundaries (`segmentPerPage` forces one segment per page); hierarchy 5 levels; **zero-shot — "no training dataset is needed"**; output `segments[]` with `startPageNumber`, `endPageNumber`, `category`, `confidence`, `source`, `segmentId`. `2026-06-01-preview` adds layout-aware classification and `allowInPageSegments` (split a single page into multiple segments). `omitContent: true` returns only segment results. — [Classifier concept, ms.date 2026-07-09](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/concepts/classifier); [Classifier how-to, ms.date 2026-07-20](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/how-to/classification-content-understanding-studio)
- Parent `models` are used only for segmentation/classification; each sub-analyzer uses its own models. Classification incurs model calls (token cost) per pricing explainer. — [Analyzer reference](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/concepts/analyzer-reference)

**Modes**
- Standard (default): low latency, confidence + grounding, extract/classify/generate, max 100 fields per the modes page (service limits page says 1,000). ### Inferences
- CU is the right primary engine for this POC: zero-label schema extraction, native per-field confidence + polygon grounding (satisfies "cell-level lineage" with `spans` + `source`), zero-shot classification/splitting of multi-carrier bundles via `contentCategories` + `enableSegment`, and native XLSX/CSV/DOCX input (at $0.01/1K pages). Treat `2025-11-01` GA as the production API and use `2026-06-01-preview` only for experiments (agentic mode, in-page segmentation, distilled training).
- "Bootstrap labels cheaply" is explicitly supported: Studio's Auto-label runs the zero-shot analyzer and lets a human correct; one sample per carrier template is Microsoft's guidance. In the 2026-06-01-preview, training also lowers per-call tokens (and the benchmark shows ~51% lower modeled cost) — a strong argument for labelling a dozen carrier templates once the schema stabilizes.
- The 300-page/200 MB async limit comfortably covers 15 MB and 50 MB batches, but the 1,000 pages/minute S0 quota is the first throughput ceiling for 25 concurrent underwriters uploading 50 MB bundles (e.g., 25 × 200-page bundles = 5,000 pages → ≥5 minutes of quota). Plan for a quota increase or multiple resources.
- Cost per 10-page scanned loss run on CU ≈ $0.05 (Layout) + $0.01 (contextualization) + ~$0.10–0.20 of gpt-5.2 tokens ≈ **$0.15–0.30**, versus DI custom extraction at $0.30 for the same 10 pages before any LLM.
- XLSX/CSV through CU returns no `source` polygons (no rendered page), so lineage for spreadsheets must be cell-address based (sheet/row/col) captured by your own parser, or you render the sheet to PDF first.

## Key Question 4: Orchestration — Durable Functions vs Logic Apps vs Container Apps+queues vs Foundry Agent Service vs Agent Framework

### Takeaway
Durable Functions (.NET isolated, Flex Consumption plan) backed by the GA Durable Task Scheduler is the pragmatic, production-credible choice: it natively provides fan-out/fan-in, retries, and `WaitForExternalEventAsync` + durable timers for human-in-the-loop waits, with an RBAC-secured dashboard, 1 MB payload limit (store documents in Blob and pass references), and Consumption pricing of $0.003 per action. Microsoft Agent Framework (`Microsoft.Agents.AI` 1.25.0 stable) is the successor to Semantic Kernel but its durable-workflow package is still preview; Foundry Agent Service's workflow agents are preview and not built for document pipelines; Logic Apps works (there is a CU connector) but is low-code and per-action-billed.

### Cited Findings

**Durable Functions / Durable Task Scheduler**
- Patterns: `await context.WaitForExternalEventAsync<bool>("Approval")` pauses an orchestration indefinitely (no max wait stated); raise with `client.RaiseEventAsync(instanceId, "Approval", true)` or `POST /runtime/webhooks/durabletask/instances/{id}/raiseEvent/{event}`; events are at-least-once (include unique IDs); "On the Consumption plan, no charges accrue while an orchestrator awaits an external event." Note: in-process .NET model reaches end of support **10 Nov 2026** — use isolated worker. — [External events, ms.date 2026-10-12](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-external-events)
- Human-interaction-with-timeout sample (isolated): `context.CreateTimer(context.CurrentUtcDateTime.AddSeconds(90), cts.Token)` raced with `WaitForExternalEvent` via `Task.WhenAny`, cancel the timer afterwards; Durable Task SDK version uses `TimeoutHours` (default 24). — [Phone verification sample, ms.date 2026-10-12](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-phone-verification)
- Timers: ".NET and Java apps support arbitrarily long timers" (JS/Python/PowerShell limited to 6 days); use `context.CurrentUtcDateTime`; cancel unused timers; a when-any timeout does not stop in-flight activities. — [Durable timers, ms.date 2026-10-12](https://learn.microsoft.com/en-us/azure/durable-task/common/durable-task-timers)

### Inferences
- Recommended POC shape: Flex Consumption Functions app (.NET 10 isolated) + DTS Consumption scheduler; one orchestration per upload; sub-orchestration per detected document (after CU classification/segmentation); activities for unlock/convert, CU analyze (poll inside activity, or use the SDK's `WaitUntil.Completed`), canonical mapping, validation, persistence; `WaitForExternalEventAsync("ReviewDecision")` with a 24-h timer for low-confidence fields; dashboard = free "observability" demo. At $0.003/action, a 50-document batch with ~10 activities each costs well under $2 in orchestration.
- Keep all CU/DI JSON in Blob and pass blob URIs — the 1 MB DTS payload limit (and 45 KB Azure Storage threshold) will be hit by a single Layout result for a 30-page scan.
- Agent Framework is worth a small "chat over claims" demo using the stable `Microsoft.Agents.AI` core, but do not put the preview `DurableTask` package on the critical path; Semantic Kernel is in successor-announced state and should not be chosen for new code.

## Key Question 5: Storage and data layer — Blob immutability, Cosmos DB vs Azure SQL, AI Search, Purview

### Takeaway
Blob Storage with version-level WORM/legal hold ($0.0184/GB-month Hot LRS) is a credible immutable source-document store (SEC 17a-4/FINRA/CFTC assessed); Cosmos DB serverless ($0.25 per 1M RUs, single-region) fits a POC for claim records + lineage JSON with change feed as an event log, while Azure SQL ledger tables give cryptographic tamper-evidence if auditors prefer relational; Azure AI Search (Basic $0.101/h ≈ $74/month) with the GA Content Understanding skill gives the chat/Q&A layer; Purview provides catalog/column-level lineage but is not designed for per-cell document extraction lineage, so lineage belongs in your own data model.

### Cited Findings
- Immutable Blob Storage (ms.date 2026-08-18): time-based retention (1 day to 146,000 days) and legal hold; container-level or version-level WORM (version-level requires versioning, not supported with hierarchical namespace); locked policies can only be extended (container-level max 5 times); assessed by Cohasset for **SEC 17a-4(f), FINRA 4511, CFTC 1.31(c)-(d)**; no extra capacity charge; policy audit logs retained for the policy lifetime; incompatible with point-in-time restore and NFS/SFTP accounts. — [Immutable storage overview](https://learn.microsoft.com/en-us/azure/storage/blobs/immutable-storage-overview)
- Blob prices (Retail, East US 2, Hot LRS): data stored **$0.0184/GB-month** (first 50 TB), write ops $0.05/10K, read ops $0.004/10K. — [price API (blob)](https://prices.azure.com/api/retail/prices?api-version=2023-01-01-preview&$filter=armRegionName%20eq%20'eastus2'%20and%20productName%20eq%20'General%20Block%20Blob%20v2'%20and%20skuName%20eq%20'Hot%20LRS')
- Cosmos DB serverless: billed per RU consumed + storage, no minimum; single region only; max 5,000 RU/s per physical partition; recommended for prototyping/intermittent traffic and Functions integration; example math $0.25 per 1M RUs vs provisioned $0.008 per 100 RU/s-hour. ## Key Question 7: Edge inputs — password-protected PDFs, spreadsheets, deskew/rotation, multi-carrier bundle splitting

### Takeaway
Neither DI nor CU opens password-protected PDFs ("remove the lock before submission"), so unlock in .NET with PdfPig (Apache-2.0, `ParsingOptions.Password`) and rasterize with PDFtoImage (PDFium/SkiaSharp) when needed; read XLSX/XLS/XLSB/CSV with ExcelDataReader (MIT, supports workbook passwords) or ClosedXML; CU also ingests XLSX/CSV natively at $0.01/1K pages (one sheet = one page) but returns no polygons for them; both services report page `angle` and handle rotated tables but do not document auto-deskew; bundle splitting is zero-shot in CU via `contentCategories` + `enableSegment`, or trained (≥5 samples/class, `splitMode=auto`) in DI.

### Cited Findings
- DI: "Password-locked PDFs: you must remove the lock before submission." — [Read input requirements](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/read?view=doc-intel-4.0.0)
- AI Search CU skill: "Password-locked PDFs: Remove the lock before indexing"; "DOCX and PDF can produce different image results. Convert to PDF if you need consistent behavior." — [AI Search CU skill](https://learn.microsoft.com/en-us/azure/search/cognitive-search-skill-content-understanding)
- PdfPig 0.1.16 (22 Aug 2026), Apache-2.0, targets .NET 6/.NET Standard 2.0/.NET Framework 4.6.2 (compatible net8/net9): open encrypted PDFs with `new ParsingOptions { Password = "..." }` or a `Passwords` list; `PdfMerger.Merge(...)`; `PdfDocumentBuilder.AddPage(document, pageNumber)` to copy pages. — [NuGet PdfPig](https://www.nuget.org/packages/PdfPig)
- PDFtoImage 5.4.0 (16 Aug 2026), MIT, PDFium + SkiaSharp, `SavePng/ToImage/ToImagesAsync`, targets .NET 8/.NET Standard 2.1; password parameter not shown on the NuGet page. — [NuGet PDFtoImage](https://www.nuget.org/packages/PDFtoImage)
- ExcelDataReader 3.9.0 (16 Jun 2026), MIT, .NET 8/.NET Standard 2.0–2.1/.NET Framework 4.6.2: reads .xlsx, .xlsb, .xls (BIFF2–8), .csv; configuration `Password` "used to open password protected workbooks." — [NuGet ExcelDataReader](https://www.nuget.org/packages/ExcelDataReader)
- ClosedXML 0.105.1 (25 Jul 2026), MIT, .NET Standard 2.0/2.1; .xlsx/.xlsm only; password support not documented. — [NuGet ClosedXML](https://www.nuget.org/packages/ClosedXML)
- CU native spreadsheet/CSV input: XLSX/XLS/XLSM/ODS and CSV/TSV accepted (≤200 MB / 10M chars); billed "Minimal" at $0.01/1K pages with one sheet (incl. hidden) = one page; no `source` polygons for non-rendered inputs; `enableOcr: false` recommended for digital PDFs. — [CU service limits](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/service-limits); [CU elements](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/document/elements); [Analyzer reference](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/concepts/analyzer-reference)
- DI: XLSX accepted by Read/Layout/classifier but "table analysis isn't supported for XLSX input"; each worksheet = one billable page. — [Layout model](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0)
- Rotation/skew: DI pages return `angle`; "rotated tables are supported"; no auto-deskew statement. CU pages return `angle` ("overall text angle in degrees, for rotated pages"); polygons are "relative to the element's natural orientation." — [Layout model](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0); [CU elements](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/document/elements)
- Bundle splitting: CU zero-shot `contentCategories` (≤200, descriptions, `other`, per-category `analyzerId`, `enableSegment`, confidence + `source` per segment; in-page segmentation in `2026-06-01-preview`); DI custom classifier needs ≥5 samples per class and `splitMode=auto`. — [CU classifier](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/concepts/classifier); [DI custom classifier](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/train/custom-classifier?view=doc-intel-4.0.0)
- Azure OpenAI vision alternative for classification: Microsoft's document-processing samples classify with GPT-4.1 vision or embedding similarity and detect page boundaries for invoices/1040s; confidence from OCR confidence + `logprobs`. — [azure-ai-document-processing-samples](https://github.com/Azure-Samples/azure-ai-document-processing-samples)

### Inferences
- Pre-processing stage in .NET: (1) sniff type; (2) PdfPig unlock with a configured password list (carrier portal exports often use a shared password) and re-save; (3) for scans, optionally rasterize with PDFtoImage at ~200 DPI and let CU/DI handle rotation (both return `angle`; test whether skewed 30-page scans degrade before adding an OpenCV-style deskew); (4) for XLSX/CSV, parse with ExcelDataReader into a row/column model, synthesize cell addresses as lineage, and send a rendered or CSV-text form to CU for schema mapping — or send XLSX directly to CU at $0.01/1K pages and rely on `spans` only.
- Treat CU's classifier as the first stage for every upload (cheap, zero-shot, returns page ranges + confidence); route `LossRun` segments to the loss-run analyzer and everything else to `other`.

- No vendor-neutral benchmarks were found on how DI/CU handle severely skewed or rotated scans (the search budget was exhausted before independent blogs could be fetched).
- PDFtoImage password support and DPI options not confirmed on NuGet (check the GitHub README).

## Key Question 9: Realistic latency and the "real-time quote" target

### Takeaway
Microsoft publishes no absolute latency numbers for DI Layout or CU document analysis (only async polling guidance of 1–5 s intervals, a 5-minute indexer timeout for CU, and a relative latency index showing CU 2.0 preview ≈ DI and ≈ 2× faster than CU 1.0 GA); for GPT calls the only published model is TTLT = TTFT + TBT × output tokens, so a 10-page document extraction returning a few hundred structured tokens is dominated by input processing and typically completes in seconds, not minutes. The end-to-end budget must therefore be measured in the POC and designed as asynchronous with progressive results.

### Cited Findings
- DI Layout: "poll Get Analyze Layout Result every 3 to 5 seconds until status is succeeded." ### Inferences
- Design the API as "accept upload → return job id immediately → stream per-document/per-claim results as orchestration steps complete," so that a 15 MB upload can show first claims within tens of seconds while a 50 MB mixed batch finishes in the background; the acceptance targets should be phrased as p95 time-to-first-result and time-to-complete, measured in the POC with the `x-ms-diagnostics` header and Azure Monitor TTLT/TBT metrics.
- Parallelize per document (sub-orchestrations) and per page-range (CU `pages` parameter or `segments`) rather than per bundle; with 25 concurrent underwriters, the CU 1,000 pages/min quota and the gpt-5.2 250K TPM default quota (Tier 1) are the two numbers to raise (or use Provisioned) before a load test.
- Without a published benchmark, the honest statement for evaluators is: "Layout/OCR of a 30-page scan and a GPT-5.2 structured extraction over it each run in the order of seconds to low tens of seconds; CU 2.0 preview is benchmarked by Microsoft at roughly DI Layout latency (index 4.9 vs 4.4) and half of CU 1.0 GA."

- No absolute seconds-per-page figures for DI Layout, CU analysis, or gpt-5.x on Azure were found in official docs; the search budget prevented collecting independent measurements. These must be measured in the POC.
- Provisioned-throughput latency SLA definition and PTU minimums per model could not be fetched (onboarding page failed); only the $1.00/$1.10/$2.00 per PTU-hour prices were retrieved.

## Retry layers (brief 33, ADR 0028)

Each layer retries what it can recover, and the Durable layer retries only what `config/retry-policy.json` classifies as transient. The figures are from the code, or captured from the SDK defaults in brief 33 (`tools/capture-failures`).

| Layer | Retries | How many | What it costs |
|---|---|---|---|
| Blob read-modify-write (`ObjectStore.UpdateAsync`) | 409 / 412 (ETag conflict) | up to 20 attempts | storage transactions only |
| Azure Storage SDK pipeline (`BlobClientOptions`) | 408, 429, 5xx, network errors | 5 retries, 0.8 s exponential to 60 s (captured defaults) | storage transactions only |
| Content Understanding client pipeline | 408, 429, 5xx on submit and on each poll; Retry-After honoured; a poll is re-sent, never the analyze | `ContentUnderstanding__MaxAttempts` (5), exponential to 60 s; Azure.Core's captured default is 3 retries from 0.8 s | a 429 is not billed; one completed analyze is |
| EF Core on Azure SQL (`LossRunDbContext`) | serverless resume and timeouts (`SqlConnections.ResumeErrors`: 40613, -2, 258, 40197, 40501) | 8 × ≤ 15 s (Entra), 3 otherwise | none |
| Embedding client (`AzureOpenAiEmbeddingService`) | 429 | 5 attempts, Retry-After or 2ⁿ s to 30 s | one metered call per success; the fingerprint embedding is cached per document, so a retried Route pays nothing |
| Learn / delta model (`LearnModel`) | 429, 500, 502, 503 | 8 attempts, Retry-After or 2ⁿ s to 60 s | billed per completed call; never retried at the Durable layer |
| Durable retry handler (`ActivityRetry.Storage`) | transient classes only (`retry-policy.json`); permanent and unknown fail at once | 3 attempts, 5 s × 2, ≤ 60 s total | ParseFile reuses stored CU results (quantity-0 `reused` rows), Route its stored embedding; every other activity is idempotent |
