# Carrier Format Memory: "Learn Once, Replay Deterministically" Techniques for Minimizing LLM Calls in Loss Run Extraction

Scope note: research notes for a workers' comp loss run ingestion POC on Azure (.NET). Nine key questions follow the assignment. Where the literature is about invoices/receipts/web pages rather than loss runs, that is stated explicitly; the techniques transfer but the accuracy numbers do not. Searches hit the per-turn web-search budget near the end, so a few items (TWIX paper, exact current Azure image-token formulas, OpenAI tile-token docs) are recorded as gaps rather than guessed.

## Key Question 1: Format fingerprinting — detecting "this is carrier X, format version Y"

### Takeaway
The strongest 2025-2026 evidence favors a learned first-page embedding (contrastive, layout-aware) compared to per-format centroids with a high cosine threshold; Amazon's CACHE-ED2 reports 100% format-detection hit rate across 50+ templates with this approach, whereas a naive text/OCR-string fingerprint (CACHE-ED1) averaged only 47% on real invoices because trivial OCR variance ("AMAZON SITE" vs "AMAZON FC SITE") caused cache misses. For spreadsheets, a normalized header-row signature is the pragmatic equivalent; for scanned PDFs, hybrid text+layout encoders (LayoutLM, Donut) cluster templates well on clean data but degrade sharply under scan noise, which is exactly the year-to-year/scanner-to-scanner variance a loss run pipeline will see.

### Cited Findings
- CACHE-ED2 (Amazon, ICML 2026 SCALE workshop) uses a "Document Format Encoder": a LiLT-base backbone with a frozen body and a 3-layer MLP projection head (~590K trainable params, 0.47% of total) trained with triplet margin loss; the first page is embedded and compared to format centroids by cosine similarity with threshold τ = 0.95; intra-class similarity 0.9954 vs inter-class 0.3704 (gap 0.625). Matches route to the stored program M[v,f]; unmatched docs trigger the generation agent — [CACHE-ED2 paper PDF](https://cdn.amazon.science/7b/83/8b6d627f4346b8df584f7b587922/scipub-approval152129-47230154-cacheed2-compiling-llm-reasoning-into-reusable-extraction-programs-for-document-extraction-at-scale.pdf)
- Format-detection (cache-hit) rates: CACHE-ED1 (string/OCR-based) on FATURA's five difficulty tiers: 0.89, 0.72, 0.57, 0.44, 0.25; CACHE-ED2: 1.0 in every tier. On 5 real vendors: CACHE-ED1 0.14/0.29/0.70/0.70/0.52 (avg 0.47); CACHE-ED2 1.0 for all five, "a 2.1× improvement." The paper attributes CACHE-ED1's misses to OCR variance such as "AMAZON SITE" vs "AMAZON FC SITE" — [CACHE-ED2 paper PDF](https://cdn.amazon.science/7b/83/8b6d627f4346b8df584f7b587922/scipub-approval152129-47230154-cacheed2-compiling-llm-reasoning-into-reusable-extraction-programs-for-document-extraction-at-scale.pdf)
- CACHE-ED2 limitation: the encoder works on single-page input; multi-page context is listed as future work; the perfect hit-rate claim is only tested on FATURA and five real invoice vendors in one vertical — [CACHE-ED2 paper PDF](https://cdn.amazon.science/7b/83/8b6d627f4346b8df584f7b587922/scipub-approval152129-47230154-cacheed2-compiling-llm-reasoning-into-reusable-extraction-programs-for-document-extraction-at-scale.pdf)
- Unsupervised template clustering study (arXiv 2506.12116, 2025): on clean FATURA (10,000 invoices, 50 templates) Gemma3-4B + BIRCH reached ARI 1.0, LayoutLMv1 + BIRCH 0.9996, Donut + k-Means 0.9708; without an oracle k, DiT and Donut with DBSCAN exceeded ARI 0.90. On "Transformed FATURA" (noise, shadows, folds, ink artifacts) the best fell to SBERT + k-Means 0.7378 and ColPali + k-Means 0.7176, and DiT/Donut "fell sharply." On 250 real scanned Mexican death certificates (9 templates) Donut + HDBSCAN+kNN scored 0.9749. Authors conclude no single model wins everywhere, pure-vision models (DiT) are brittle under degradation, and "no clustering algorithm fixes a poorly aligned embedding space" — [arXiv 2506.12116](https://arxiv.org/pdf/2506.12116)
- Evaporate (Stanford/VLDB 2024) notes that simple TF-IDF + K-means clustering "recovered the source website of SWDE documents perfectly," suggesting templates can be grouped automatically with text-only features when the vocabulary per source is distinctive — [Evaporate, PVLDB vol 17](https://www.vldb.org/pvldb/vol17/p92-arora.pdf)
- Sensible's SenseML uses a declarative `fingerprint` block: a list of text tests that run before any field extraction (e.g., GEICO config checks every page for the text "geico" with partial match); a config activates only if all tests pass and non-matching documents fall through to a generalized config, so caller code needs no routing logic — [Sensible blog: insurance declaration pages](https://www.sensible.so/blog/how-to-extract-data-from-insurance-declaration-pages-with-sensible)
- Automation Anywhere patent US11804056 ("Document spatial layout feature extraction to simplify template classification"): detects page objects (logos, headers, addresses, table structure) with an object recognizer/OCR, filters to "significant" objects, converts each to a vector from a page corner, sequences objects top-to-bottom/left-to-right into a 1-D array of (type, size, shape), and compares to known-format arrays with Levenshtein distance against an adjustable threshold — [Google Patents US11804056](https://patents.google.com/patent/US11804056)
- Azure Document Intelligence custom classification model (v4.0 2024-11-30 GA): minimum 2 classes and 5 samples per class; max 1,000 classes and 100 samples/class; supports PDF, images, DOCX/XLSX/PPTX (Office files not in Studio); `splitMode` = none | perPage | auto for multi-document files; incremental training via `baseClassifierId` to add classes; returns a per-document `confidence` (e.g., 0.97); docs recommend adding an "other" class or a confidence threshold for unknown types — [MS Learn: custom classifier](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/train/custom-classifier)
- Custom classification is priced at roughly $3 per 1,000 pages per one third-party tracker (verified Oct 2026) but ~$10 per 1,000 pages per a Microsoft moderator's Q&A answer (Dec 2025); the official pricing page rendered only "$-" placeholders in this fetch — [aiproductivity.ai pricing tracker](https://aiproductivity.ai/pricing/azure-document-intelligence); contradicted by [MS Q&A answer](https://learn.microsoft.com/en-us/answers/a/12439288)
- Azure-Samples document-processing repo includes a "semantic similarity classification using vector embeddings from Azure OpenAI embedding models" sample (and a GPT-4.1 vision classifier) in both Python and .NET — [Azure-Samples/azure-ai-document-processing-samples](https://github.com/Azure-Samples/azure-ai-document-processing-samples)
- Heron Data (loss run parser) says it "identifies the carrier layout" by looking for common insurance phrases, table structures and header patterns, and tracks exception rates "by carrier template" — [Heron Data: parse for loss runs](https://www.herondata.io/action-guides/parse-for-loss-runs)

### Inferences
- A two-tier fingerprint is the practical design: (1) a cheap deterministic key — for XLSX/CSV a hash of the normalized header tuple (lower-cased, punctuation stripped, whitespace collapsed) plus sheet count; for PDFs a hash of the Layout model's `title`/`pageHeader` paragraph roles plus the first table's column-header cells; and (2) a fallback embedding (text-embedding-3-small/large over the first page's Layout markdown, or a vision embedding) compared to per-carrier-format centroids with a high threshold (CACHE-ED2 used 0.95). The deterministic key catches exact repeats for free; the embedding absorbs OCR jitter.
- The transformed-FATURA results imply that year-to-year layout changes and scan-quality changes will produce a different "cluster" for a vision-only embedding; text-based (SBERT/ColPali) embeddings are more robust to visual noise, which argues for fingerprinting on Layout-extracted text rather than raw pixels for scanned loss runs.
- Document Intelligence's custom classifier is viable as the carrier-level classifier (dozens of carriers, 5+ samples each) but it classifies document *type*, not format *version*; version detection should be a second, cheaper step (header signature diff) inside the carrier.
- Hit rate matters more than accuracy for cost: CACHE-ED2's token savings (62%) vs CACHE-ED1 (31%) at the same program quality were driven almost entirely by the format-detection hit rate.

### Gaps
- No source quantified year-to-year format-change frequency for insurance carriers' loss runs; the template-free vendors assert it happens but give no rates.
- No published evaluation of Azure Document Intelligence custom classification accuracy on same-type/different-vendor documents (vendor A invoice vs vendor B invoice); its docs only state that similar classes need more samples.
- The exact current Azure price of custom classification is contradicted across sources ($3 vs ~$10 per 1,000 pages); the official page did not render prices in this fetch.

## Key Question 2: Schema/column-mapping memory — per-carrier mappings, normalization rules, versioning, drift, partial matches, and schema-matching literature

### Takeaway
Treat the per-carrier mapping as a versioned, declarative artifact (source header → canonical field + normalization rule + code-set mapping) and bootstrap new mappings with a retrieve-then-rerank schema matcher: embedding/BM25 retrieval over an LLM-enriched glossary of canonical fields, then a small LLM reranks the top-k. Published results on hard biomedical benchmarks (SCHEMORA HR@5 80.4%, Magneto MRR 0.866 vs ≤0.45 for classical matchers) show LLM-enriched synonyms are the single largest contributor; for a loss run glossary of ~30 canonical fields the problem is far easier than those benchmarks.

### Cited Findings
- SCHEMORA (2025) matches columns with off-the-shelf LLMs and no labeled data: it enriches target columns with two LLM prompts (expand cryptic names; generate alternative names that avoid source wording, e.g., "ward_id" → "location id"), indexes with FAISS over embeddings plus a BM25 index, retrieves top-50 candidates (cosine ≥ 0.5 / BM25 ≥ 1), has an LLM filter candidates by table relevance, then an LLM ranks. On MIMIC-OMOP: HR@1 54.25%, HR@3 72.55%, HR@5 80.39% vs ReMatch 42.5/63.8/72.9 and SMAT 6–11% HR@1. Ablations: removing query enrichment drops HR@5 to 42.11%; removing name expansion drops it to 67.32%; GPT-4.1 beat GPT-4.1-mini by ~10% HR@5; bge-small (384-d) "performed close to the larger models" — [SCHEMORA arXiv 2507.14376](https://arxiv.org/html/2507.14376v1)
- Magneto (NYU, 2024): retrieval with a small language model (MPNet) embedding "column name + type + up to 10 sampled values", exact-name matches scored 1.0, then an LLM (GPT-4o-mini default) reranks top-k=20 with 0.00–1.00 scores, with 3 retries and fallback to embedding scores on parse failure; fine-tuned with LLM-generated synthetic variants (abbreviations, synonyms, naming-convention variants, e.g., "masked_somatic_mutations" → "genetic_variants") using triplet loss. On the GDC benchmark (736-column target) the best classical method reached ≤0.45 MRR while Magneto-ft-llm reached 0.866 MRR; LLM reranking at k=5 raised MRR 0.731 → 0.780. Runtime: Magneto-zs-bp 11–33 s per table; Magneto-zs-llm 545–589 s; reranking all pairs with GPT-4o took >6,000 s per table and scored lower — [Magneto arXiv 2412.08194](https://arxiv.org/html/2412.08194)
- SMUTF (2024): combines LLM-generated HXL-style tags, rule-based name features (BLEU, Damerau-Levenshtein, LCS ratio, containment, name-embedding cosine), value features (type indicators, length/numeric stats, char ratios, averaged text embeddings) and a fine-tuned MPNet, classified by XGBoost (16-fold ensemble, default threshold 0.10–0.15); reports +11.84% F1 and +5.08% AUC over existing methods; training data augmented with masked names ("col3") to reduce reliance on headers — [SMUTF arXiv 2402.01685](https://arxiv.org/html/2402.01685v3)
- Prompt-Matcher (2024): uses GPT-4 to verify individual correspondences (yes/no + 0–1 confidence) to reduce entropy over a set of candidate matchings produced by seven classical matchers; "Abbreviation-Match" prompt (domain context + abbreviation hints + sample-value exchange) scored 91.8% on the abbreviated-names Fabricated-Dataset vs 70% for plain "Semantic-Match"; budget-constrained selection is NP-hard, greedy (1−1/e) approximation; one update raised a view's probability 0.55 → 0.647 and cut entropy 0.997 → 0.351 — [Prompt-Matcher arXiv 2408.14507](https://arxiv.org/pdf/2408.14507)
- Sensible's loss run doc-type page shows the concrete pattern of synonym lists in config: "claim number, claim #, claim ID" and "date of loss, DOL, loss date"; it states "Each layout requires its own extraction configuration," new formats configure "in hours," and under managed services engineers "update them when formats change" — [Sensible: loss runs doc type](https://www.sensible.so/doc-types/loss-runs)
- CACHE-ED2 stores validated programs in a "DocExDSL Store M" indexed by format and partitioned by business vertical; each field carries a "document-processed score" that increments with each successful match against human-validated output; score-guarded updates make the critic skeptical of contradicting corrections once a field's score exceeds 5 (a due-date rule with 78 validations rejected a 1-day human correction as likely error) — [CACHE-ED2 paper PDF](https://cdn.amazon.science/7b/83/8b6d627f4346b8df584f7b587922/scipub-approval152129-47230154-cacheed2-compiling-llm-reasoning-into-reusable-extraction-programs-for-document-extraction-at-scale.pdf)
- Schema-drift handling patterns from data-engineering practice: types of drift (additive fields, removals, type changes, structural, renames like `user_id` → `customer_id`); detection by logging schema hashes/diffs between inferred schema snapshots and contract validation; handling by permissive ingestion at capture + strict validation at boundaries, tagging records with a schema version, publishing incompatible changes to a new versioned collection, and reviewing inferred schema changes under version control instead of auto-accepting — [Estuary: schema drift](https://estuary.dev/blog/schema-drift/)
- Azure Document Intelligence Layout marks table cells with `kind` (e.g., `columnHeader`) and notes header cells "can span multiple rows and aren't necessarily the first rows in a table"; table analysis is not supported when the input is XLSX — [MS Learn: Layout model](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0)

### Inferences
- Concrete per-carrier mapping record (pseudo-design) suggested by the sources above:
  ```
  CarrierFormat {
    carrierId, formatId, version, createdFrom (docId), status (active|superseded),
    fingerprint { headerSignatureHash, firstPageEmbedding[], titleTokens[] },
    fileKind (xlsx|csv|pdf-text|pdf-scan),
    tableLocator { sheetName|tableIndex, headerRowIndex, dataStartRow, stopRule },
    columnMap[] { sourceHeader, sourceColIndex, canonicalField, confidence,
                  normalizer (dateFmt|currency|percent|enumMap|trim),
                  enumMap { "O":"open","C":"closed","RO":"reopened" } },
    derivedRules[] { "total_incurred = paid_total + reserve_total" },
    validationRules[] { "sum(paid_total) == reportTotalPaid ± 1.00", "claimCount == reportClaimCount" },
    fieldScores { canonicalField -> successCount },   // CACHE-ED2 style
    lineage { learnedBy (model, promptVersion), reviewedBy, supersedes }
  }
  ```
- Partial matches: when the deterministic replay maps, say, 24 of 27 headers and 3 are unknown, only the unknown headers need an LLM call (a "delta mapping" call with the glossary), not the whole document — this is the cheapest drift-recovery path and is consistent with SEED's "LLM as last-resort per record" and CACHE-ED2's per-field scores.
- Because the canonical schema is small (≈30 fields) and the carrier vocabulary is bounded, a BM25 + embedding retrieval over an LLM-expanded synonym glossary will likely resolve most headers with no LLM call at all; reserve the reranking LLM for ambiguous ties (e.g., "Expense" could be ALAE paid or ALAE incurred depending on the adjacent columns).
- Version the mapping, never mutate it: a new `formatId.version` is created when a re-learn happens; the old version remains attached to documents already processed (lineage), matching the versioned-schema practice above.

### Gaps
- No open-source .NET library for semantic column mapping was found; the cited systems (Magneto, SCHEMORA, SMUTF) are Python research code. Magneto's code is at github.com/VIDA-NYU/magneto-matcher per the alphaXiv page, but it was not fetched.
- No paper evaluates schema matching specifically on insurance loss run headers; the reported numbers are from biomedical/open-data benchmarks and will not transfer directly.
- No source gives a concrete "partial header match" policy with thresholds; the pseudo-design above is an inference.

## Key Question 3: LLM-synthesized extractors (code/spec once per format, executed deterministically)

### Takeaway
This is the best-evidenced pattern: Evaporate (2023/VLDB 2024) showed LLM-written extraction functions cost ~110× fewer tokens than per-document LLM extraction and, with weak-supervision ensembling, beat direct extraction by +10 F1; SEED (MIT, 2023/24) showed an "LLM-as-compiler" pipeline answering 60–100% of records without LLM calls; and Amazon's CACHE-ED2 (2026) moved from raw code to a constrained DSL (strategies → candidates → disambiguation → transforms → validation) with an agent that iterates against the execution engine, reaching 0.99 accuracy with 1.0 extraction rate on real invoices and 62% cumulative token reduction over 1,000 docs. Single unverified functions are unreliable (Evaporate: >40% of generated functions scored <25 F1), so verification/ensembling or an agentic test loop is mandatory.

### Cited Findings
- Evaporate (Arora et al., Stanford; arXiv 2304.09433, PVLDB vol 17): Evaporate-Direct prompts the LLM per document chunk (quality high, cost linear in corpus size); Evaporate-Code has the LLM synthesize extraction functions from a small sample (cost fixed w.r.t. corpus size but ~13.8 F1 lower than Direct); Evaporate-Code+ generates many candidate functions and aggregates with weak supervision (Algorithm 1: LLM outputs on ~10 sample docs serve as noisy ground truth; functions scoring ≤0.5 discarded; a label model combines votes). Results: Code+ uses ~110× fewer tokens than Direct on average (range ~35×–217× across settings, assuming 10k docs), crossover at roughly 40 documents; OpenIE Pair F1 (text-davinci-003): Direct 56.6, Code+ 66.7 (+10.1 F1); Code+ beats prior SOTA by 3.2 F1 end-to-end. Failure modes: >40% of generated functions fall below 25 Text F1 and ~half below 50; functions lack abstention logic so null can mean "absent" or "function too weak"; Code+ is high-precision/lower-recall; attributes with no surviving function are dropped. Functions run in ~0.00025 s per document on 2 CPUs; "functions transfer well because attribute-value formatting is consistent within a source" — [Evaporate PVLDB](https://www.vldb.org/pvldb/vol17/p92-arora.pdf)
- SEED (MIT, arXiv 2310.00749): "LLM-as-compiler" producing a hybrid pipeline of CodeGen (ensembles + evolutionary refinement, no runtime LLM calls), CacheReuse (answer from cached LLM results above a similarity threshold), ModelGen (small model trained on LLM labels), and direct LLM; modules ordered by priority score (1 − fallback probability)/cost with a user-set effectiveness gap G. Results: entity resolution Amazon-Google F1 76.2 using 10.4% LLM calls (vs MatchGPT Generic 76.4 at 100%); Abt-Buy 88.0 at 2.9% LLM calls; data imputation Restaurant 84.7 with 0.0% LLM calls (CodeGen only) vs 88.4 for LLM; data extraction Wiki-NBA token F1 88.6 vs 84.7 for Evaporate-Code+ and 84.6 for Evaporate-Direct, with ~22.5% of cases reaching the LLM; data annotation batching cut LLM calls by 99% and tokens by 95% vs per-record calls — [SEED arXiv 2310.00749](https://arxiv.org/html/2310.00749v3)
- CACHE-ED2 (Bhoi, Tripathi, Raza, Jauhari — Amazon; ICML 2026 SCALE workshop): repositions the LLM "from instance-level analyst to system-level developer." Components: DocExDSL (Python-embedded, Pydantic; per-field stages Strategies → Candidates → Disambiguation → Transforms → Validation; five strategy types key-based, anchor-based, table, region, derived, chained as ordered fallbacks); deterministic Execution Engine over a typed document graph (KEY, VALUE, TEXT, TABLE, CELL nodes) with sub-second, zero-inference processing; a ReAct code-generation agent that never extracts values directly but calls the engine as a tool and checks results against the full-resolution page image; a single-turn HITL critic that converts analyst corrections into program edits. Baseline per-document LLM extraction is characterized as 3–5 s latency and "$4–5 per page." Results (all methods using Claude Sonnet 4.6): CORD v2 average accuracy LLM-alone 0.91, CACHE-ED1 0.98, CACHE-ED2 0.99; real invoices (5 vendors × 1,000) LLM-alone ~0.64 on SOP-dependent fields, vendor-SOP prompts 0.96, CACHE-ED1 0.81, CACHE-ED2 0.99 with 1.0 extraction rate on all seven fields. Tokens: baseline ~13,360 tokens/doc (~13.4M per 1,000 docs); CACHE-ED2 ~5M per 1,000 docs (~62% reduction, "∼2.6×"); CACHE-ED1 ~9M (~31%); both caching methods beat baseline cumulative cost after ~50 documents. No dollar figures reported; cache hits are "zero LLM calls" — [CACHE-ED2 paper PDF](https://cdn.amazon.science/7b/83/8b6d627f4346b8df584f7b587922/scipub-approval152129-47230154-cacheed2-compiling-llm-reasoning-into-reusable-extraction-programs-for-document-extraction-at-scale.pdf); venue/abstract at [ICML 2026 virtual page](https://icml.cc/virtual/2026/67417)
- CACHE-ED2 limitations the authors list: evaluated on five production vendors in one vertical; encoder is single-page; cold start for new vendors (cross-vendor pattern sharing is future work); fixed DSL; it is a workshop paper on internal data; Algorithm 1 does not describe an explicit LLM fallback when a cached program fails at runtime — [CACHE-ED2 paper PDF](https://cdn.amazon.science/7b/83/8b6d627f4346b8df584f7b587922/scipub-approval152129-47230154-cacheed2-compiling-llm-reasoning-into-reusable-extraction-programs-for-document-extraction-at-scale.pdf)
- AutoScraper (EMNLP 2024): LLM generates reusable XPath action sequences via progressive top-down/step-back traversal and synthesizes across several seed pages; with GPT-4-Turbo on SWDE it reaches 71.56% executable-correct vs 61.88% CoT and 67.50% Reflexion, IE F1 88.69 vs 78.56 for direct extraction — but direct extraction beat AutoScraper for every weaker LLM tested (GPT-3.5-Turbo 75.76 direct vs 69.20); break-even ≈19.5 pages per site; failure modes: non-generalizable rules, multi-valued targets, text-predicate XPath fragility — [AutoScraper arXiv 2404.12753](https://arxiv.org/html/2404.12753v2)
- XPath Agent (2025): two-stage (weak LLM extracts values + cue texts; strong LLM writes XPath from condensed HTML of three seed pages, up to three feedback loops); page sanitization shrinks HTML to 10–20% of original size; GPT-4o F1 0.8514; the paper reports no token-savings percentage vs a baseline — [XPath Agent arXiv 2502.15688](https://arxiv.org/pdf/2502.15688)
- invoice2data (open source): `--new-template sample.pdf --ai --template-out acme.yml` asks an LLM provider to propose the regexes for a YAML/JSON template you "own"; templates are tried first and the LLM runs only when no template matches or a matched template misses required fields (`--ai-fallback`); only document text is sent, never page images — [invoice2data AI docs](https://invoice2data.readthedocs.io/latest/ai.html)
- Sensible's production split: LLM-based methods (Query Group, List) reason over the document and work on unfamiliar layouts; layout-based methods (Region, Row, Regex) are deterministic and make no LLM call; the article says to build a carrier-specific template when a carrier has high volume, an accuracy gap, or a sub-second latency need; a GEICO template took "under an hour" — [Sensible blog: declaration pages](https://www.sensible.so/blog/how-to-extract-data-from-insurance-declaration-pages-with-sensible)
- Sensible loss run case study: an underwriting platform built ~300 per-carrier loss run templates in-house ("300+ extraction templates", tens of thousands of documents/month, template count grew from ~50 to hundreds); the article says deterministic methods "worked well for loss runs" and LLM approaches "struggle to provide that precision for dense, complex loss runs"; a hybrid is used for ACORD forms (LLM cleans difficult OCR, deterministic methods extract) — [Sensible: two insurance companies](https://sensible.so/blog/how-two-insurance-companies-expedited-underwriting-with-automated-loss-run-processing)

### Inferences
- For loss runs the "program" to synthesize is mostly a *table spec*, not free-form regex: which sheet/table, which row is the header, how to detect continuation pages and subtotal rows, the column map, and derived/validation rules. A constrained declarative spec (CACHE-ED2's DSL idea, Sensible's SenseML idea) is safer than arbitrary generated C#/Python because it can be validated, diffed, versioned and executed in-process in .NET without sandboxing generated code.
- The agentic loop matters: CACHE-ED2's jump from 0.81 (ED1) to 0.99 (ED2) on real invoices came from having the agent execute its program and compare against the page before storing it. A POC should have the LLM emit the spec, run it on the same document, feed back validation failures (totals mismatch, unmapped columns), and iterate up to N times before persisting.
- Evaporate's failure statistics (>40% of single functions <25 F1) mean "LLM writes one regex and we trust it" is not credible; either ensemble several candidate specs and vote (Evaporate-Code+), or test the spec against the learning document's own report totals (cheaper and loss-run-specific).
- Break-even points reported (Evaporate ~40 docs, AutoScraper ~19.5 pages, CACHE-ED2 ~50 docs) all assume an expensive learn step; with a 20-page loss run, a single learn call can already pay for itself on the *same* document if the replay path handles pages 2–20 deterministically.

### Gaps
- No peer-reviewed study of LLM-synthesized extractors on insurance loss runs specifically; the invoice/receipt/web results are the closest.
- A paper referred to in several listings as "TWIX" (reconstructing structured data from templatized documents, reportedly orders of magnitude cheaper than LLM-per-document) could not be located (three arXiv id guesses returned unrelated papers; the search budget was exhausted). Not cited.
- No dollar figures for CACHE-ED2; only token counts.

## Key Question 4: Hybrid routing / confidence gating (template path vs small model vs big model)

### Takeaway
Raw LLM logprobs and verbalized confidence are poorly calibrated for field extraction (AUROC 0.54–0.74 in a 2026 study), but fused, calibrated multi-signal scores (OCR confidence, cross-call agreement, value grounding, layout/validation checks) reach AUROC 0.90–0.99 and allow 49–72% of fields to be auto-approved at <10% error; per-field validation (regex, range, allowed values, cross-field arithmetic) should run deterministically on every document including cache hits. For loss runs, reconciliation to the report's own printed totals is the strongest free signal.

### Cited Findings
- "Beyond Logprobs" (arXiv 2606.24420, 2026): two structurally different GPT-4o calls per field (field-guided "Hunter" and document-guided "Mapper") feed a CatBoost classifier with 14 logprob/entropy features, Textract OCR word confidences, value-in-OCR grounding, candidate competition at 50/75/90% similarity, cross-call agreement (exact/Levenshtein/fuzzy), spatial features and field type. On DocILE (1,339 fields, 26.6% natural failure rate): logprob-mean baseline AUC 0.705 / ECE 0.245; verbalized confidence AUC 0.692; 5× self-consistency AUC 0.744 / ECE 0.075; full model AUC 0.928, AURC 0.043; isotonic recalibration cuts ECE to 0.034 (−83%). At 80% coverage, automated accuracy is 99.1% vs 73.3% base rate. Zero-shot CORD AUC 0.858. Re-extraction with a larger model is not studied — [arXiv 2606.24420](https://arxiv.org/pdf/2606.24420)
- "Perception, Layout, and Validation" (arXiv 2609.20110, Sept 2026): three confidence channels (perception, layout, validation) combined with a conformal risk-control step; native VLM verbalized confidence AUROC 0.54–0.74 vs 0.90–0.99 for the decomposed score; at a target error <10%, auto-approved (STP) fields rise from 0.1–7.0% to 49–72% while empirical error stays at or below target; models Qwen3.6-27B and Gemini-3.1-Flash-Lite; three public datasets (real invoices, synthetic invoices, ad-buy forms) — [arXiv 2609.20110 abstract](https://arxiv.org/abs/2609.20110)
- CACHE-ED2 validation: five deterministic constraint types (pattern/regex, length, range, allowed values, custom predicates) plus cross-field custom validators such as "line items summing to the header total"; validation "runs even on cache hits" and is "fully deterministic, LLM-free"; failures are flagged for review without halting; per-field diagnostics (candidates, strategy outcome, validation errors) feed the agent's self-debugging loop — [CACHE-ED2 paper PDF](https://cdn.amazon.science/7b/83/8b6d627f4346b8df584f7b587922/scipub-approval152129-47230154-cacheed2-compiling-llm-reasoning-into-reusable-extraction-programs-for-document-extraction-at-scale.pdf)
- SEED's optimizer orders modules by (1 − fallback probability)/cost, each module either answers or passes the record on, and the LLM "typically is the last step in the execution pipeline, always answers"; low-confidence records fall back to it — [SEED arXiv 2310.00749](https://arxiv.org/html/2310.00749v3)
- Microsoft's Azure document-processing samples compute a confidence score "based on OCR analysis confidence and `logprobs` in Azure OpenAI responses" (helper at `samples/dotnet/modules/samples/confidence/OpenAIConfidence.csx`), in response to a user asking how to trigger human review for LLM extraction when traditional ML gave per-field confidence — [Tech Community reply](https://techcommunity.microsoft.com/discussions/azurepartners/evaluating-the-quality-of-ai-document-data-extraction-with-small-and-large-langu/4157719/replies/4375120); repo at [Azure-Samples](https://github.com/Azure-Samples/azure-ai-document-processing-samples)
- Microsoft's SLM-vs-LLM evaluation (June 2024) found "confidence" (logprob-based) above 99% even where accuracy was 67–79% (e.g., GPT-4o Mini Vision on an insurance policy: 67.25% accuracy, 98.73% confidence), illustrating the miscalibration — [Microsoft Tech Community blog](https://techcommunity.microsoft.com/blog/azureforisvandstartupstechnicalblog/evaluating-the-quality-of-ai-document-data-extraction-with-small-and-large-langu/4157719)
- Loss-run-specific validation used by vendors: Heron Data checks "totals and ratios … against per-claim sums and carrier conventions," keeps both figures with a discrepancy note when a summary total conflicts with line items, and requires multi-period packets to form continuous date ranges — [Heron Data](https://www.herondata.io/action-guides/parse-for-loss-runs); Outmarket "compares extracted totals with the totals stated in the document and flags variances" — [Outmarket blog](https://outmarket.ai/blog/outmarket-ai-launches-ai-powered-loss-run-extraction-and-analysis); Nomad Data flags "incongruent counts between narrative and tabular sections" — [Nomad Data](https://www.nomad-data.com/doc-chat/unlocking-cross-carrier-prior-losses-in-submission-documents-portfolio-manager); Concirrus says "Totals, calculations and claim details validated" — [Concirrus](https://concirrus.ai/loss-run-intelligence/)
- Azure Document Intelligence Layout returns word-level `confidence` (e.g., 0.997), handwriting `isHandwritten` + confidence, and selection-mark confidence, usable as the OCR-quality signal — [MS Learn: Layout](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0)
- Actuarial identities usable as validators: incurred (a.k.a. reported) loss = paid loss + case reserve; ALAE is claim-specific expense; ULAE "isn't found in a loss run"; claim status is open/closed/reopened and some loss runs show "incident only" — [Milliman glossary](https://www.milliman.com/en/insight/a-beginners-guide-to-the-casualty-actuarial-language); WCIRB defines incurred indemnity/medical as "paid plus outstanding reserves as of the valuation date" — [WCIRB USR handbook 2023](https://www.wcirb.com/sites/default/files/documents/2023_sept_data_reporting_handbook-usr.pdf)

### Inferences
- A loss-run routing policy grounded in the above (pseudo-design):
  1. Fingerprint hit AND header signature exact → deterministic replay (no model).
  2. Replay succeeds AND validators pass (per-claim sums = printed totals within rounding; paid+reserve=incurred per row; claim count matches; dates parse; status ∈ enum; all required canonical fields mapped) → auto-accept.
  3. Replay runs but ≥1 validator fails or ≤N headers unmapped → "delta" call to a small model (gpt-5-mini/nano class) with only the unmapped headers/sample rows + glossary; re-validate.
  4. Fingerprint miss, or small-model delta fails, or OCR mean word confidence below threshold, or scanned pages with handwriting → big model learn path (vision + Layout markdown) producing a new format version; re-validate; persist.
  5. Any remaining validator failure → human review queue with page/cell citations.
- Because printed totals exist on most loss runs, the loss run domain can get an unusually strong deterministic confidence signal without the two-call/CatBoost machinery; the published calibration work is most relevant for fields with no arithmetic check (status, injury codes, dates).
- Logprob-based confidence should be treated as a weak feature, not a gate, given the 99%-confidence/67%-accuracy pattern in Microsoft's own test.

### Gaps
- No published calibration study on loss run or claims-listing documents; the invoice results are a proxy.
- No source gives recommended numeric thresholds for OCR confidence or embedding similarity for routing in production; CACHE-ED2's 0.95 cosine is the only concrete threshold found.

## Key Question 6: Spreadsheets (multi-tab XLSX/CSV) — deterministic parsing, header detection, when an LLM is needed

### Takeaway
Spreadsheet loss runs should almost never need a per-document LLM call: parse natively in .NET, detect the header row heuristically (first row whose cells are mostly non-numeric strings that resolve against the glossary), hash the header tuple as the fingerprint, and map via the glossary; the LLM is needed only for (1) a never-seen header set, (2) multi-table or stacked-header sheets where header-row detection is ambiguous, and (3) headerless/"report-style" exports. Azure Document Intelligence Layout does not do table analysis on XLSX, so native parsing is the only deterministic path for Excel.

### Cited Findings
- Azure Document Intelligence Layout: "Table analysis isn't supported when the input is XLSX"; XLSX is billed as 1 worksheet = 1 page unit; DOCX/HTML up to 3,000 characters = 1 page unit — [MS Learn: Layout](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0)
- Content Understanding bills digital files (DOCX, XLSX, HTML, TXT) always on the cheapest "Minimal" content-extraction meter — [MS Learn: CU pricing explainer](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/pricing-explainer)
- messytables (open source): scans the first few rows of a sample to guess the header row (`headers_guess` returns an offset and headers), applies an offset processor to skip past it, and guesses column types "by attempting to convert all members of a given column into all types and searching for the best match"; the scoring algorithm is not documented — [messytables docs](https://dataproxy.readthedocs.io/)
- SpreadsheetLLM's structural-anchor heuristic: keep heterogeneous rows/columns near likely table boundaries and drop distant homogeneous ones — removes ~75% of content while keeping >97% of boundary rows/columns; table-detection F1 ~78.9% with a fine-tuned GPT-4 (open-source Llama 3/Mistral ~72%); evaluation was small (188 spreadsheets) and cell formatting (colors, borders) is not encoded — [SpreadsheetLLM](https://huggingface.co/papers/2407.09025.md)
- TableSense (Microsoft Research, AAAI 2019) is the prior CNN-based spreadsheet table-detection baseline SpreadsheetLLM compares against — [TableSense arXiv](https://arxiv.org/pdf/2106.13500)
- Sensible's loss run config handles multi-page claim tables by stitching rows across pages into one output and treats synonyms declaratively ("claim number, claim #, claim ID") — [Sensible: loss runs](https://www.sensible.so/doc-types/loss-runs)
- IntellectAI claims its loss run extraction handles "borderless tables and headerless sheets" and has been tested on "over 1,000 carrier formats" (vendor claim, no methodology) — [IntellectAI Loss Runs Overview PDF](https://www.intellectai.com/wp-content/uploads/2024/05/Loss-Runs-Overview.pdf)
- The lossrx R package's sample loss run uses 30 flat columns such as `eval_date`, `loss_date`, `rept_date`, `status`, `claim_type`, `cause`, `total_paid`, `total_incurred`, `occurrence_number`, with WC amounts split into Indemnity/Medical/Expense — a realistic shape for a carrier CSV export — [lossrx docs](https://jimbrig.r-universe.dev/lossrx/doc/Lossruns-and-Triangles.html)

### Inferences
- Deterministic XLSX path (pseudo-design): for each sheet → find candidate header rows (rows where ≥60% of non-empty cells are strings, followed by a row with ≥1 numeric/date cell); score each candidate by fraction of cells resolving to the glossary (exact → synonym → embedding ≥ threshold); choose the best; everything below until a blank row or a row whose first cell matches /total|subtotal|grand/i is data; subtotal rows are excluded from claims but captured as `reportTotals` for reconciliation. Header tuple hash + sheet name → fingerprint. Multi-tab files: each tab classified as claims | summary | policy | other by its header resolution ratio.
- Trigger LLM only when: header resolution ratio < ~80%, two candidate header rows score similarly (stacked headers like "Indemnity | Medical" over "Paid | Reserve | Incurred"), or no header row found; then send the LLM the first ~15 rows (SpreadsheetLLM-style compressed) with the glossary and ask for a mapping spec, which is stored as a new format version.
- Stacked/grouped headers (very common on WC loss runs: group header "Indemnity" spanning "Paid/Reserve/Incurred") need a composite header key (parent + child) in the mapping, not just the bottom row.

### Gaps
- No .NET-specific library for header detection was found; messytables/SpreadsheetLLM are Python/research. Implementation would be custom on top of ClosedXML/EPPlus.
- No published accuracy for deterministic header detection on insurance exports.

## Key Question 7: Handling drift — detection signals, automatic re-learning, lineage

### Takeaway
Drift is detected cheaply by (1) fingerprint/header-signature mismatch within a known carrier, (2) deterministic validation failures on replay (unmapped headers, totals not reconciling, enum/date parse failures, extraction-rate drop), and (3) embedding similarity falling between the "known format" and "new format" thresholds; recovery is a scoped re-learn that produces a new format version while the old version is retained for lineage, with CACHE-ED2-style per-field success scores to resist over-reacting to one-off anomalies.

### Cited Findings
- CACHE-ED2 attributes CACHE-ED1's failures to OCR variance causing cache misses ("AMAZON SITE" vs "AMAZON FC SITE") and designs the learned encoder to absorb such differences; within a program, strategies fall back in declared order (broken key-value links → anchor-based search; truncated anchors → fuzzy key matching); on an analyst-corrected mismatch, the critic recommends changes, the agent regenerates the program, "scores for changed fields reset, and the program is re-stored"; fields with score >5 make the critic skeptical of contradicting corrections — [CACHE-ED2 paper PDF](https://cdn.amazon.science/7b/83/8b6d627f4346b8df584f7b587922/scipub-approval152129-47230154-cacheed2-compiling-llm-reasoning-into-reusable-extraction-programs-for-document-extraction-at-scale.pdf)
- invoice2data falls back to the LLM when "no template matches or a matched template misses required fields" — the "matched but incomplete" case is the drift signal — [invoice2data AI docs](https://invoice2data.readthedocs.io/latest/ai.html)
- Evaporate notes that functions lack abstention logic, so a null output can mean "attribute absent" or "function too weak" — a reason to track per-field extraction *rate* as a drift signal rather than null-equals-missing — [Evaporate PVLDB](https://www.vldb.org/pvldb/vol17/p92-arora.pdf)
- AutoScraper's documented failure mode: a rule that works on most pages fails on a page where the target sits in a different node (e.g., a "Not Available" value), and text-based XPath predicates "often break on new pages" — [AutoScraper](https://arxiv.org/html/2404.12753v2)
- Data-engineering practice: log schema hashes / diff inferred schemas between runs; validate records against a contract so violations surface immediately; tag records with a schema version; publish incompatible changes to a new versioned collection; review inferred changes in version control rather than auto-accept — [Estuary: schema drift](https://estuary.dev/blog/schema-drift/)
- Heron Data tracks exception rates "by carrier template" and says "training sets and thresholds are adjusted for those formats," with a weekly spot-check loop that adds low-confidence examples back into training — [Heron Data](https://www.herondata.io/action-guides/parse-for-loss-runs)
- Sensible managed services "update them [configs] when formats change"; Sensible also observes carriers differ in where totals appear ("One carrier puts totals on the first page; another buries them at the end") — [Sensible: loss runs](https://www.sensible.so/doc-types/loss-runs)
- Template-free vendors argue templates "fail when the document format changes" and need ongoing upkeep, but provide no frequency data — [Hypatos](https://www.hypatos.ai/knowledge-base/template-free-document-extraction-enterprise); [Bevaya/Roots](https://www.bevaya.ai/blog/why-ocr-alone-isnt-enough-for-insurance-document-processing)
- Document Intelligence custom classifiers support incremental training (`baseClassifierId`) to add samples/classes without retraining from scratch (v4.0 2024-11-30) — [MS Learn: custom classifier](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/train/custom-classifier)

### Inferences
- Drift taxonomy for loss runs and the cheapest detector for each: (1) header rename/add/remove → header-signature diff (free); (2) column reorder → map by name not position (free); (3) new code values (status "RO", new cause codes) → enum validation failure (free); (4) layout move (totals block moves, table split across pages differently) → Layout table-structure diff + totals reconciliation failure (Layout cost only); (5) new carrier/TPA branding or new report generator → fingerprint miss (embedding).
- Re-learn scope should match the drift: header-level drift → small-model "delta mapping" on only the unknown headers; structural drift → full learn path on the first 2–3 pages with the previous version's spec supplied as a prior ("here is how v3 mapped this carrier; produce v4"), which is cheaper and more consistent than learning from scratch.
- Keep `formatVersion` on every extracted claim row and never delete superseded versions (lineage/audit, and needed to reproduce historical extractions). A per-field success counter (CACHE-ED2) distinguishes "this field has reconciled 78 times, one failure is probably the document" from "this field is new and untested."
- Alert thresholds: a carrier whose replay validation pass-rate drops below its trailing baseline (e.g., 95% → 70% over N documents) is drift even when individual documents still parse.

### Gaps
- No quantitative study of how often carrier loss run formats change year to year; vendor claims are qualitative.
- No source describes using the prior mapping as a prior for re-learning; that is an inference.

## Key Question 8: Glossary bootstrapping — canonical WC loss run glossary from public standards and the LLM

### Takeaway
There is no public, standardized loss run *format* (a 2002 RIMS-era standardization effort is the only trace found), but the *field semantics and code sets* are well standardized: WCIRB/NCCI Unit Statistical Reporting defines claim-level fields and injury-type/status codes, and the WCIO Injury Description Tables (Part of Body / Nature of Injury / Cause of Injury, 2-digit codes) are the de facto code sets referenced by ACORD, California WCIS and state FROI instructions; actuarial glossaries fix the arithmetic (incurred = paid + case reserve). Synonym lists per canonical field are not published anywhere found and must be assembled from vendor config examples plus LLM expansion (the SCHEMORA/Magneto technique).

### Cited Findings
- WCIRB Unit Statistical Reporting handbook (Sept 2023): claim-level fields include Claim Number (must not change once reported; sole key for matching), Accident Date (YYMMDD), Claim Count, Claim/Status Code (0 = Open, 1 = Closed; no separate "reopened" code — reopenings handled via subsequent-report revaluation), Injury Code (01 Death, 02 Permanent Total, 03 Major Permanent Partial, 04 Minor Permanent Partial, 05 Temporary Total/Partial, 06 Medical Only, 07 Contract Medical, 08 Compromised Death), Paid Indemnity, Paid Medical, Incurred Indemnity ("paid plus outstanding reserves as of the valuation date"), Incurred Medical, Paid ALAE; other code sets: Type of Loss (01 Trauma, 02 Occupational Disease, 03 Cumulative Injury), Type of Recovery, Type of Claim (WC only / EL only / both), Type of Settlement (incl. 06 Compromise and Release), Fraudulent Claim Code, Vocational Rehab indicator; Injury Description Codes are 2-digit with Part of Body in positions 1–2, Nature in 3–4, Cause in 5–6; WCSTAT (WCIO specifications) governs technical field attributes — [WCIRB USR handbook 2023](https://www.wcirb.com/sites/default/files/documents/2023_sept_data_reporting_handbook-usr.pdf)
- WCIO Part of Body table (as published by Utah Labor Commission, headed "Workers Compensation Insurance Organizations Injury Description Codes"): Head 10–19 (10 Multiple Head Injury, 11 Skull, 12 Brain, 13 Ear(s), 14 Eye(s)…), Neck 20–26 (21 Vertebrae, 22 Disc, 23 Spinal Cord), Upper Extremities 30–39 (31 Upper Arm, 32 Elbow, 34 Wrist, 35 Hand, 36 Finger(s), 38 Shoulder(s)), Trunk 40–49 and 60–63 (41 Upper Back, 42 Lower Back, 44 Chest, 48 Internal Organs, 61 Abdomen, 63 Lumbar &/or Sacral Vertebrae), Lower Extremities 50–58 (51 Hip, 53 Knee, 55 Ankle, 56 Foot, 57 Toes), Multiple/Other (64 Artificial Appliance, 65 Insufficient Info, 66 No Physical Injury, 90 Multiple Body Parts, 91 Body Systems, 99 Whole Body) — [Utah WCIO Part Table PDF](http://laborcommission.utah.gov/wp-content/uploads/2019/11/WCIO_Part_Table.pdf)
- WCIO Nature and Cause codes (Alabama FROI instructions, linking wcio_nature_table.pdf / wcio_cause_table.pdf): Nature 01 No Physical Injury, 02 Amputation, 04 Burn, 07 Concussion, 10 Contusion, 28 Fracture, 40 Laceration, 49 Sprain or Tear, 52 Strain or Tear, 59 All Other Specific Injuries NOC, 60–80 Occupational Disease (61 Asbestosis, 68 Dermatitis, 74 Cancer, 78 Carpal Tunnel); Cause 01 Chemicals, 04 Fire or Flame, 10 Machine or Machinery, 17 Object Being Lifted or Handled, 25 From Different Level (Elevation), 31 Fall/Slip/Trip NOC, 45 Collision with Another Vehicle, 56 Lifting, 57 Pushing or Pulling, 60 Strain or Injury By NOC, 75 Falling or Flying Object, 77 Motor Vehicle, 78 Moving Parts of Machine, 99 Other Miscellaneous NOC — [Alabama WC FROI codes PDF](https://www.labor.alabama.gov/docs/forms/wc_froi%20codes.pdf)
- California WCIS states it categorizes injuries using the WCIO Injury Description Tables for part of body, cause and nature (examples: Low Back Area (Lumbar and Lumbo-Sacral), Lifting, Strain or Tear) and notes "these codes are not medical diagnoses" — [CA DIR WCIS tables](https://www.dir.ca.gov/dwc/wcis/WCIS_tables/Tables1-3/WCIS_Reports-Table1-3.html)
- ACORD P&C ClaimsInjury aggregate: `BodyPartCd` (sources WCIO or OSHA), `BodyPartDesc`, `InjuryNatureCd`, `InjuryNatureDesc`, `InjurySeverityCd`, `LossCauseCd` (sources WCIO, ISO, BLS), `LossCauseDesc`, `ImpairmentPct` — [PilotFish ACORD model viewer](https://modelviewers.pilotfishtechnology.com/modelviewers/ACORD-PCS/model/ClaimsInjury.html)
- Some states use their own schemes: Minnesota's 2015 injury coding guide uses 3-digit codes (e.g., Nature 160 Contusion/Crush/Bruise, 310 Sprains/Strains; Cause 020 Struck By, 120 Overexertion; Part 420 Back, 700 Multiple Parts) and does not attribute them to WCIO/NCCI — a reason the glossary must support multiple code systems per carrier — [Minnesota WC injury coding guide](https://mn.gov/admin/assets/wc_injury_coding_tcm36-209466.pdf)
- Actuarial definitions: paid loss = amount received as of the evaluation date; case reserve = adjuster's estimate of remaining payments; incurred loss (a.k.a. reported loss) = paid + case reserve; ALAE = claim-specific expense; ULAE not on a loss run; indemnity = lost-time/wage benefits vs medical; claim status "closed, open, or reopened," sometimes "incident only"; "evaluation date" — [Milliman glossary](https://www.milliman.com/en/insight/a-beginners-guide-to-the-casualty-actuarial-language)
- Typical loss run fields per the lossrx package: unique claim ID, occurrence ID, claimant name, evaluation date, date of accident/loss, date of report, report lag, hire date, close/re-open dates, claim status, claim type (e.g., "Indemnity," "Medical Only," "Closed no Pay"), litigation, location, total reported/incurred, total paid, total reserve, and for WC the Indemnity/Medical/Expense split of paid, case reserve and incurred — [lossrx docs](https://jimbrig.r-universe.dev/lossrx/doc/Lossruns-and-Triangles.html)
- Vendor canonical schemas: Sensible — policy number, insured, effective/expiration, carrier (+NAIC), LOB; claim number, date of loss, cause, status (open/closed), paid, reserve, total incurred, coverage, location; totals (claim count, open count, paid/reserve/incurred totals, frequency, severity) — [Sensible: loss runs](https://www.sensible.so/doc-types/loss-runs); Heron — carrier, policy number, insured, effective/expiration, claim number, date of loss, paid to date, incurred, reserve remaining, status, last transaction date, rollups and boolean quality flags — [Heron Data](https://www.herondata.io/action-guides/parse-for-loss-runs); Nomad Data "maps disparate carrier codes into a common taxonomy" and harmonizes cause/status including litigation, subrogation, salvage — [Nomad Data](https://www.nomad-data.com/doc-chat/unlocking-cross-carrier-prior-losses-in-submission-documents-portfolio-manager)
- The only trace of an industry-wide loss-run *format* standard is a 2002 trade-press article about "a group working to establish a loss-run standard for risk managers"; the article body could not be retrieved — [PropertyCasualty360, 2002](https://propertycasualty360.com/2002/04/15/rms-closing-in-on-loss-run-standard)
- LLM-generated synonym expansion is the mechanism with the strongest measured effect in schema matching (SCHEMORA: removing name expansion drops HR@5 from 80.4% to 67.3%; Magneto: synthetic abbreviation/synonym variants used to fine-tune the retriever) — [SCHEMORA](https://arxiv.org/html/2507.14376v1); [Magneto](https://arxiv.org/html/2412.08194)

### Inferences
- Canonical schema skeleton suggested by the standards above: identifiers (claim_number, claimant_name, occurrence_id, policy_number, insured_name, carrier, tpa); dates (loss_date, report_date, close_date, reopen_date, valuation_date, policy_effective, policy_expiration); classification (claim_status {open, closed, reopened, incident_only}, claim_type / injury_type {medical_only, indemnity/lost_time, death, PT, PPD, TTD…}, litigation_flag, subrogation_flag, jurisdiction_state); injury codes (part_of_body_code + system, nature_code + system, cause_code + system, with free-text descriptions); financials for each of indemnity, medical, expense/ALAE, and total × {paid, reserve/outstanding, incurred} plus recoveries/subrogation; report-level totals and claim counts for reconciliation.
- Bootstrapping steps: seed each canonical field with 5–15 synonyms from the vendor examples and standards (e.g., incurred: "Total Incurred," "Incurred," "Reported," "Case Incurred," "Inc"; reserve: "O/S," "Outstanding," "Reserves," "Case Reserve," "Remaining"; indemnity paid: "Ind Paid," "Indemnity Paid," "Comp Paid," "BI Paid," "Lost Time Paid"; loss date: "DOI," "DOL," "Date of Injury," "Accident Date," "Loss Date"); then ask the big model once to expand each field with abbreviations and carrier-style variants (SCHEMORA's second prompt: avoid reusing the canonical words); then grow the glossary from every learned mapping (each confirmed sourceHeader → canonicalField pair is appended with its carrier provenance).
- Code-set mapping must be per code *system* (WCIO 2-digit, state-specific 3-digit, carrier-internal text), stored alongside the mapping with a `codeSystem` tag; free-text descriptions can be matched to WCIO descriptions by embedding when a carrier exports text only.

### Gaps
- No public synonym list / data dictionary for loss run column headers was found; vendor pages show only a handful of examples. The glossary must be built in-house.
- NCCI's own data specifications (e.g., WCSTAT/USR manuals) are behind membership walls; the WCIRB handbook and state FROI pages were the accessible proxies. The full WCIO Nature and Cause tables were not fetched in their entirety.
- The ACORD Loss Run form/standard content itself was not retrievable; only the ClaimsInjury XML aggregate was captured.

## Key Question 9: Evidence from real systems (insurtechs/carriers caching carrier formats, reducing model calls)

### Takeaway
Public evidence is thin but consistent: the one detailed production write-up (Sensible's customer with ~300 per-carrier loss run templates) explicitly chose deterministic per-carrier templates over LLM extraction for loss run precision; CogniSure publicly described "training the top 25 carrier loss run formats" in 2020; Amazon's CACHE-ED2 is the only peer-reviewed production-scale account of caching per-format extraction programs with measured token savings. Most insurtech marketing (Nomad Data, Concirrus, Outmarket, IntellectAI, Quantiphi, Heron) claims "any format" with 95–99% accuracy but discloses no mechanism for carrier memory.

### Cited Findings
- Sensible case study: Company B (an underwriting platform) estimated ~300 loss run formats, built nearly all templates in-house after training, grew from ~50 to hundreds of templates, processes "tens of thousands of documents each month"; article's conclusion: deterministic extraction for loss runs because LLM approaches "struggle to provide that precision for dense, complex loss runs." Company A (insurtech, WC loss runs, low volume) used managed services; "long loss runs that previously required hours now process automatically within seconds." No accuracy or cost figures — [Sensible: two insurance companies](https://sensible.so/blog/how-two-insurance-companies-expedited-underwriting-with-automated-loss-run-processing)
- Sensible's insurance page: a customer (Shepherd) claims "100%" accuracy on supported loss run formats and 300+ page loss runs processed in under a minute; the caller specifies the SenseML config matching the carrier format; per-document pricing regardless of page count — [Sensible insurance page](https://www.sensible.so/insurance)
- CogniSure (2020): "trained the top 25 carrier loss run formats," targeting the top 100 carriers by end of 2020; patent-pending algorithms normalize extracted data into a common loss run format; no accuracy figures — [Crowdfund Insider, Sept 2020](https://www.crowdfundinsider.com/2020/09/167176-u-s-insurtech-cognisure-debuts-ai-platform-for-commercial-loss-run-automation/)
- Amazon CACHE-ED2: deployed-style evaluation on 5,000 production invoices from 5 vendors with per-format cached programs; 0.99 accuracy, 1.0 extraction rate, ~62% cumulative token reduction over 1,000 documents, zero LLM calls on cache hits; HITL corrections converted to program edits with score-guarded updates — [CACHE-ED2 paper PDF](https://cdn.amazon.science/7b/83/8b6d627f4346b8df584f7b587922/scipub-approval152129-47230154-cacheed2-compiling-llm-reasoning-into-reusable-extraction-programs-for-document-extraction-at-scale.pdf)
- Persistent Systems case study (specialty insurer, Google Cloud): Vision API OCR → standard text format → AutoML entity extraction trained on labeled data; precision 98.72%, recall 98.81%, accuracy 98.76%; fields included carrier, claim number, feature type, payment status, reserve, recoveries; no per-carrier templates mentioned ("even newer file formats showed some level of consistency") — [Persistent case study](https://www.persistent.com/client-success/a-leading-specialty-insurance-provider-automates-data-extraction-from-its-loss-run-reports-with-ml/)
- Quantiphi loss run automation (agentic): ingestion "classifies documents by carrier, policy type, and format"; OCR → ML extraction → LLM orchestration layer; claims "up to 99% extraction accuracy on complex loss runs," files >7,000 pages, processing/training time reduced "up to 40%"; no template/memory mechanism named — [Quantiphi blog](https://quantiphi.com/blog/loss-run-automation/)
- Nomad Data DocChat: "maps disparate carrier codes into a common taxonomy," encodes customer "playbooks into Doc Chat presets," implementation 1–2 weeks, "hours to minutes per file," no stated accuracy rate and no claim of caching carrier formats — [Nomad Data](https://www.nomad-data.com/doc-chat/unlocking-cross-carrier-prior-losses-in-submission-documents-portfolio-manager)
- Concirrus Loss Run Intelligence: "99% extraction accuracy," "95% faster processing," complex files under five minutes, PDFs/spreadsheets/images accepted; no mechanism disclosed — [Concirrus](https://concirrus.ai/loss-run-intelligence/)
- Outmarket AI: handles any carrier PDF format, automated discrepancy detection against document totals, side-by-side review; no accuracy percentage; no claim of learning formats — [Outmarket blog](https://outmarket.ai/blog/outmarket-ai-launches-ai-powered-loss-run-extraction-and-analysis)
- IntellectAI Magic Submission: tested on "over 1,000 carrier formats," ">95%" headline accuracy (elsewhere "~100%"), 43-page loss run read in under 9 minutes, humans in the loop to prevent hallucinations — [IntellectAI PDF](https://www.intellectai.com/wp-content/uploads/2024/05/Loss-Runs-Overview.pdf)
- Heron Data: carrier-layout identification, exception tracking by carrier template, weekly low-confidence review that feeds examples back to training; no accuracy numbers — [Heron Data](https://www.herondata.io/action-guides/parse-for-loss-runs)
- Hypatos (template-free IDP vendor) concedes template-free systems achieve "slightly lower accuracy" than carefully configured templates on well-known consistent formats and that templates "may win on accuracy" for a small number of stable suppliers, while offering supplier-specific fine-tuning for the highest-volume suppliers — [Hypatos](https://www.hypatos.ai/knowledge-base/template-free-document-extraction-enterprise)

### Inferences
- The market has converged on a hybrid that mirrors the research: a general LLM/ML path for the long tail and deterministic per-carrier artifacts (templates/configs/programs) for repeat high-volume carriers, with totals-based discrepancy detection as the universal validator. The main difference from the user's goal is *who* writes the per-carrier artifact: Sensible's customers wrote ~300 by hand; CACHE-ED2 has the LLM write and maintain them. The user's "learn once with the LLM, replay deterministically" plan is exactly the CACHE-ED2 position applied to loss runs.
- Vendor accuracy claims (95–100%) are unverified marketing; the only numbers with methodology are CACHE-ED2 (0.99 on invoices), Persistent (98.76% on a labeled AutoML model), and Microsoft's benchmark (invoice/insurance policy).

### Gaps
- No engineering blog from Groundspeed, Kalepa, Federato, Indico or Roots describing carrier-format caching was found; searches surfaced only marketing pages (and Roots' blog now redirects to Bevaya).
- The MIT Sloan capstone on CogniSure (which might contain template counts/accuracy) redirected to a program landing page and could not be read.
- No carrier (as opposed to vendor) has published a loss run ingestion architecture.

## Brief 30: routing and replay safeguards

- **A value that does not normalize routes to Review.** Replay drops a printed value its normalizer cannot read (an OCR'd `$1,2O0.00`, a decimal comma `0,00`). Every rule can still pass with the gap.
  - The value is now a structured issue (`ReplayResult.Unnormalized`, with page and polygon, or sheet and cell).
  - Any such issue turns ReplayAccepted into Review, the reason naming the field and where it was printed.
  - The count goes into `RoutingDecision.UnnormalizedValues` and the manifest. Kept rows of another line of business are exempt for their claim type and line.
- **Ambiguous exact keys.** Two formats can share `(identity, header)`, as two CSV exports with the same columns do. Then:
  - the submission's carrier decides;
  - if it names none, the embedding tier is tried among those formats;
  - otherwise Review: "ambiguous format: A, B". A format is never picked by version across formats.
- **Codes are checked.** The `code` normalizer checks `code-sets.json`: membership of a complete table, or width and alphabet for a partial or format-only one. It writes `codeSystem` (the field's declared WCIO table when the spec names none). Descriptive text in a code column is an issue, not a code.
- **Blank policy cells** (`periods.source: column`). The row is attached to the period above with a `periodAssignment` lineage note, and an issue unless the spec declares `periods.fillDown: true` (schema addition, default false).
- **Drift repairs verify on exemplars.** A delta (or the learn it escalates to) must also read the format's last accepted documents right (`learn-gate.json` `exemplars.count`, default 2). Accepted documents are recorded per format.
- **Spec patterns are data.** Each is compiled once, culture-invariant, with a 1 s match timeout.
- **Other replay fixes:**
  - total rows honour `nullWhen`, and their realignment uses R-10's tolerance;
  - a counts pattern that captures text is an issue;
  - recovery replays with the registry glossary and skips any candidate that throws;
  - a centroid built under another text normalization is not compared.

## Where carrier knowledge lives (ADR 0026)

**Meaning is global; layout is per format.**
- **Glossary or spec?** A header-to-field mapping goes in the glossary when it is true of the words, whoever printed them, and in the format spec when it is true of one layout.
- **When a learned mapping becomes global:** only with evidence across learned formats or a reviewer's confirmation (ADR 0019).
- **Table-dependent meanings:** a meaning that depends on the table is a conditional alias with its condition attached.
- **No carrier branches:** no code branches on a carrier's identity (below).

## Carrier identity on replay (brief 35)

- **A format knows its carrier.** That is `carrierName`, the name it was learned on, plus `carrierNames`: the carrier's other legal names, added by a reviewer and never by the learn model. A replay whose page names another carrier goes to Review with "carrier name on the page differs from the format's: …".
- **Names compare by their core.** Normalized text with the corporate words dropped (`CarrierNames.Normalize`, shared with the blind-run alignment key: Inc, Co, Company, Corp, Insurance, Assurance, Indemnity, Casualty, Mutual, Group, a trailing "of America", The). "X Indemnity Co" and "X Insurance Company" are one carrier. "X Property Casualty Co of America" needs one reviewer answer: `formatChanges carrierNames.add` publishes a version with the name and the parent's status, and the next document that prints it replays clean.
- **The learn gate refuses a carrier read from another party's label.** It refuses two document fields on one label, and a field read from a label the glossary gives another header-block field (brief 34 wake, c8: the insured delivered as the carrier).

## Carrier-generic code (brief 20 §4)

**Rule.** Carrier-specific knowledge lives in two places only:
- the learned carrier-format specs (`src/LossRun.Formats`, the registry);
- the glossary (`docs/evaluation/glossary.json`, and from ADR 0019 the learned aliases).

Code is layout-generic. Every lint rule, auto-fix, spec-language construct, ingestion detector and classifier branch reads the spec, the document graph and the glossary, never a carrier identity. A carrier that prints differently gets a different spec, not a code branch. That keeps the next carrier, and the organisation's archive, on the same path as the bake-off carriers.

**Enforced in CI.** `tools/generic-guard.sh` runs in the `sample-guard` workflow, and fails when either of these appears in `src/` outside tests, test data (`src/TestShared/`) and the synthetic corpus generator:
- **A real carrier, TPA or pool name** from `config/carrier-names.txt`, in code, comments or strings. Names are whole-word matched, case-insensitive unless the entry is marked `cs:`. The list is maintained from the glossary's sources and carrier provenance, the real samples' carrier labels, and the vendor research.
- **A condition on a carrier identity:** a carrier value compared with a string literal, `Equals` / `StartsWith` / `Contains` with a literal, or a `switch` over a carrier value.

A line may carry `generic-guard: allow (<reason>)` only when it is a scan for the names themselves, or a placeholder value such as an import's "unknown". Real samples are referred to in code comments by brief and category ("a real sample, brief 17"), never by name.

## Learned glossary aliases (brief 21, ADR 0019)

The glossary grows the way formats do, through verified learns, without code changes.
- **Candidate.** A header a verified learn mapped that the seed does not resolve. It is never used.
- **Active.** It resolves like a hand alias, after the seed. It gets there when a reviewer confirms its format, or when it has verified on 5 documents across 3 learned formats (`config/alias-policy.json`; a hand-spec replay counts toward documents, never toward formats).
- **Retired.** A correction of a value read through it, or a rejection, retires it.

**Where they live:** `dbo.GlossaryAlias` and `dbo.GlossaryAliasEvidence` (or the registry sidecar). `lossrun glossary export` writes them for review. An alias moves into `glossary.json` only by a pull request (`docs/operations/tuning-loop.md`).
